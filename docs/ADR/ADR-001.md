# ADR-001: Go, not Node.js, for the realtime server

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-07-28 *(records a decision made during initial design; see `docs/SYSTEM_DESIGN.md` §4)* |
| **Deciders** | Horizon team |
| **Supersedes** | — |

## Context

Horizon's backend does one thing: hold a long-lived WebSocket per rider, group riders into rooms by
join code, and fan out a combined state frame to everyone in the room on a fixed 4 Hz tick. On top of
that it computes standings, proxies route requests to OpenRouteService, and mints LiveKit tokens.

The shape of the workload:

- **~15 concurrent long-lived connections per ride**, a handful of rides. Tiny.
- **Fan-out, not request/response.** Each tick, one marshalled payload goes to every client in a
  room. Ingest at ~1 Hz per rider is fully decoupled from egress at 4 Hz.
- **Shared mutable state** — the rider set and the route — touched from many connection goroutines
  and one broadcast loop.
- **CPU-bound geometry**, growing: `distAlong` is O(riders × route segments) per tick, and an ORS
  cycling route for a 50 km ride can be 2,000–5,000 points.
- **Deployment on a free tier**, with a hard memory ceiling and no budget (see [ADR-006](./ADR-006.md)).

Constraints at the time of the decision:

- The team already knows TypeScript. The clients are TypeScript regardless.
- The team is willing to learn **exactly one** new language for this project.
- No paid infrastructure, so the deployment artifact should be small and cheap to run.

The real question was not "which language is fastest" — at 15 riders, everything is fast enough. It
was: **which single new language is worth learning, and where does it earn its keep?**

## Decision

**We use Go with `github.com/gorilla/websocket` for the realtime server.** Go is the *only* new
language in the project. Everything the rider sees is TypeScript.

The split is stated in `docs/SYSTEM_DESIGN.md` §4: **Go = backend brain, TypeScript = everything the rider
sees.** We do not write UI in Go (`gomobile` exists and cannot build real mobile UIs), and we do not
write the realtime server in TypeScript.

Supporting rules that follow from this and are enforced in `CLAUDE.md`:

- Standard library first. The backend has exactly **one** third-party dependency.
- All packages under `internal/`.
- `go fmt ./... && go vet ./...` clean before every commit.

## Alternatives Considered

### Node.js + Socket.IO / `ws`

**Genuinely attractive.** One language across the whole stack — no context switching, shared types
between server and client without a translation layer, the largest package ecosystem in existence,
and the team is already productive in it. `ws` is excellent. Socket.IO would have given us reconnect
logic, room primitives, and heartbeats for free — several of which we have since hand-written.

**Why it lost:**

1. **It teaches the team nothing.** The stated goal was to learn one genuinely new thing. A Node
   backend makes the project 100% TypeScript and the learning value approximately zero.
2. **The concurrency model is a worse fit.** Our workload is "many long-lived connections plus a
   periodic tick plus shared mutable state". In Go that is a goroutine per pump and a `select` over
   a ticker — the language's canonical shape. In Node it is an event loop plus timers, which works,
   but a single blocking CPU section stalls *every* connection. `distAlong` at O(R×S) per tick is
   exactly such a section, and the mitigation (worker threads, chunking) is more complex than Go's
   "run it on another goroutine".
3. **Deployment weight.** Go produces one static binary, low tens of megabytes, no runtime, near-zero
   idle memory. Node needs a runtime and a `node_modules` tree. On a free tier with a hard memory
   cap, that difference is operationally real.
4. **Dependency gravity.** The Node ecosystem's default answer to every problem is a package. Our
   backend has one dependency and we intend to keep it that way ([P5](../DEVELOPMENT_GUIDE.md#p5--keep-dependencies-minimal)).
   Go's standard library makes that easy; `net/http` with 1.22 method-pattern routing gave us the
   entire route table with no framework.

### TypeScript everywhere via Bun or Deno

Modern runtimes, first-class TypeScript, fast, batteries included. Same objection as Node on
learning value and concurrency shape, plus a smaller operational track record and thinner free-tier
hosting support. Not worth the novelty risk on the one component that must not fall over mid-ride.

### Elixir / Phoenix Channels

**On paper the best technical fit in this list.** The BEAM was built for exactly this: millions of
lightweight processes, supervision trees, per-connection isolation where one crash doesn't take
down the others. Phoenix Channels and Presence would have handled rooms, membership, and reconnect
out of the box — and would have prevented our current "one panic kills every ride" problem
structurally.

It lost on **learning cost**: functional programming plus OTP plus a new syntax is a much steeper
curve than Go, and Go's curve was already the budget. Smaller hosting ecosystem, and a much smaller
chance a future contributor already knows it.

### Rust

Best raw performance and the strongest correctness guarantees — the borrow checker would have made
our data-race questions non-questions. Rejected on development velocity: async Rust is genuinely
hard, and we do not have a performance problem that needs solving. We have a *shipping* problem.

### Python (FastAPI + WebSockets)

Fastest to prototype and the team could read it immediately. Rejected: the GIL makes CPU-bound
geometry under concurrent connections awkward, per-connection memory is high, and deployment is
heavier than either Go or Node.

### Managed realtime service (Pusher, Ably, Firebase Realtime Database)

Would have removed the backend entirely. Rejected on two independent grounds: every one of them
requires a card past a low free tier, which [ADR-006](./ADR-006.md) forbids outright — and more
fundamentally, **the realtime server is the one part of this system that is genuinely ours.** Renting
it would leave the project with nothing but glue code. We rent tiles ([ADR-003](./ADR-003.md)) and
voice ([ADR-005](./ADR-005.md)) precisely so we can afford to build this.

## Consequences

**Positive**

- The concurrency model matches the problem exactly. `room.run()` is a single goroutine doing
  `select` over `register`, `unregister`, and a 250 ms ticker; each connection gets a read pump and a
  write pump. This reads like the problem statement.
- **The whole backend is ~340 lines** across five files with one dependency. It fits in one sitting.
- Single static binary: `go build -o server .` and copy it. No runtime, no `node_modules`, trivial
  containerization, works on any free tier.
- `go vet` and the race detector are in the toolchain. `go test -race` is available the moment we
  write tests — and for concurrent code that is worth a great deal.
- Idle memory is small enough that the room leak (BUG-03) hasn't hurt us yet, which bought time.
- LiveKit's server is itself written in Go, so self-hosting it later ([ADR-005](./ADR-005.md)) keeps
  us in one ecosystem.
- Standard library `net/http` with Go 1.22 method patterns (`"POST /rides/{code}/route"`) gave us
  routing with zero framework.

**Negative**

- **The protocol is defined twice** — Go structs and `web/src/types.ts` — and will be three times
  once mobile lands. There is no shared schema and no conformance test. `heading` has already
  drifted. A Node backend would have had this for free. This is DEBT-H7 on the board and it is the
  single largest real cost of this decision.
- Two languages means two toolchains, two formatters, two test runners, two CI jobs.
- Some ceremony we'd have gotten free from Socket.IO is hand-written: ping/pong keepalive, reconnect
  backoff on the client, room membership, backpressure. All of it is small and all of it is ours to
  debug.
- Go's `net/http` gives no middleware chain out of the box, which is part of why CORS, panic
  recovery, and request logging are all still missing (BUG-05, DEBT-H5, DEBT-H6). The stdlib-first
  rule made those *easy to skip*.
- A contributor who only knows TypeScript can work on two thirds of the repo and not the third that
  matters most.

## Trade-offs

| We gave up | We got |
|---|---|
| One language across the stack | A concurrency model that matches the workload |
| Shared types between server and client | A 340-line, single-binary, single-dependency server |
| npm's ecosystem | A standard library that makes dependency minimalism easy |
| Socket.IO's free room/reconnect/heartbeat machinery | Full control over the wire protocol and backpressure policy |
| Instant productivity for a TS-only contributor | One genuinely new skill, applied where it earns its keep |

The honest summary: **we accepted protocol duplication as the price of a better concurrency model
and a smaller operational footprint.** That was the right call at this scale, and DEBT-H7 exists to
keep the bill visible.

## Future Revisions

Revisit if:

- **Protocol drift causes a real production bug.** The fix is not to change languages — it is a
  golden-fixture conformance test asserting the Go structs and `types.ts` agree, or generating one
  from the other. Do that before ever reconsidering the runtime.
- **The team loses all Go familiarity.** A backend nobody can maintain is worse than a slower one.
- **Horizontal scale becomes real.** Redis Pub/Sub between instances (`docs/SYSTEM_DESIGN.md` §9) is
  additive and language-agnostic; it does not motivate a rewrite.
- **CPU becomes the binding constraint.** Go is not the problem — the O(R×S) `distAlong` loop is
  (DEBT-H2). Fix the algorithm, not the language.

**What would *not* justify revisiting:** wanting shared types, disliking two toolchains, or a
contributor preferring TypeScript. Those costs were known and accepted here.

**Migration cost if reversed:** low, and that is worth knowing. The backend is ~340 lines with one
dependency, the protocol is fully documented in `CLAUDE.md`, and both clients would be untouched — a
rewrite in another language is a weekend, not a quarter. This decision is cheap to unwind, which is
part of why it was safe to make quickly.
