# ADR-019: Return shows facts about one ride, never comparisons

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-10 |
| **Deciders** | Horizon team |
| **Supersedes** | — |
| **Amends** | [ADR-009](./ADR-009.md) (extends its no-ranking rule from *between riders* to *between a rider's own rides* — a distinction ADR-009 had no reason to draw, since no ride history existed) |

## Context

`ADR-009` removed the race indicator and settled that Horizon ranks nothing:

> "No standings, no ranking."

That was written about riders in a convoy — the only comparison the app could make at the time.
`ADR-018` introduces a table of a rider's past rides, which creates a new axis nobody has ruled on:
**a rider compared against their own history.** "Your longest ride." "3rd fastest this year."
"You've ridden 4,210 km all-time."

None of that ranks a rider against anyone else, so `ADR-009` does not literally forbid it. All of it
is gamification, which `docs/PRODUCT.md` forbids in the strongest terms it uses anywhere — *"no
badges, achievements, streaks, leaderboards, XP, levels, artificial rewards"* — and the Return
register is described there as **reflective**, not evaluative.

This record exists because the proposal will be made. "Your longest ride" is the single most obvious
feature to add to a list of past rides, it will look harmless, and the answer should be a link
rather than a conversation. `docs/ADR/README.md` says most work needs no ADR; this is the exception
it names — a decision someone will otherwise re-open every quarter.

## Decision

### 1. The test

**Does the number require a second ride to compute? If yes, it is a ranking. It does not ship.**

That is the whole rule. It is deliberately mechanical, because "is this gamification?" invites
argument and "does this need another row?" does not.

### 2. What ships, and what does not

| Shown | Banned |
|---|---|
| Distance | Personal best, longest, fastest ever |
| Moving time, total elapsed time | "3rd longest this year" |
| Date; start and end place names | Rides this month, streaks, any count with momentum |
| The route line, and the track actually ridden | Lifetime totals as a headline figure |
| Average speed and max speed **for this ride** | Any comparison to a previous ride |
| Companions, **named** | Progress bars toward anything |
| The journal note, the photos | Any superlative; any trophy framing |

Two calls worth stating because they are the ones that get argued:

- **Max speed ships.** It is a fact about this ride, compared to nothing. It becomes a violation the
  instant it is compared to another ride — which is exactly the test in §1 doing its job, and shows
  the rule is about the *comparison*, not about the number being impressive.
- **Lifetime totals do not ship.** "4,210 km all-time" is factually a fact and functionally an XP
  bar: it only ever goes up, and its only purpose is to be watched going up. The single permitted
  aggregate is a neutral year divider in the archive list, which exists for *navigation* — finding a
  ride — not as a figure to admire.

### 3. No notification when a summary is ready

`docs/PRODUCT.md`'s Deferred Delivery principle means a finished ride's summary is **there** when the
rider next opens the app. It is not announced, badged, or counted. `CLAUDE.md`'s Do/Don't already
forbids this; it is restated because "your ride summary is ready" feels like a courtesy rather than
a notification, and it is a notification.

### 4. The rule is enforced by a type signature, not by review

`mobile/src/features/return/RideFacts.tsx` takes **one** `Ride` and renders only fields of that ride.
A statistic requiring a second ride cannot be expressed through its props.

This is the same trick `mobile/src/design/tokens.ts` already uses to ban serif typography in the
Motion register: there is no serif entry in the `motion` scale, so the violation is not available to
write. Making the wrong thing unrepresentable beats catching it in review, because review is where
this rule will eventually be relaxed by someone who does not know why it exists.

Correspondingly, `mobile/src/core/rides.ts` exposes no cross-ride aggregate query. `listRides`
returns rows for the archive list; there is no `getStats()`.

## Alternatives Considered

### Allow lifetime totals, ban only explicit rankings

The strongest version of this argument: a rider genuinely might want to know how far they have
ridden with the app, it is a true fact about them, and refusing to show it is paternalistic.
**Rejected** on function over form. A monotonically increasing number displayed prominently is an
XP bar regardless of what it is called, and `docs/PRODUCT.md` bans the mechanic, not the vocabulary.
The honest test is whether anyone would want it if it could also go down.

### Allow personal bests, ban only inter-rider comparison

Reads as a faithful application of `ADR-009`, which was explicitly about riders against each other.
**Rejected:** ranking a rider against their past self is the mechanic every fitness app uses, and
`docs/PRODUCT.md` says outright that Horizon is *"not a fitness app."* It also changes what a ride
is *for* — a rider who knows a number is watching has been given a reason to ride differently, which
is the opposite of "I barely noticed Horizon was there."

### Make it a setting, off by default

Lets riders who want stats have them without imposing on anyone. **Rejected** because a setting is a
decision not made, and the cost lands on the wrong side: the feature still has to be built,
maintained, and designed, and its existence in the settings screen is itself an advertisement for a
mechanic the product rejects.

### Write the rule into `docs/DESIGN.md` §7 instead of an ADR

Cheaper, and arguably the right home for a presentation rule. **Rejected** because it is not a
presentation rule — it is a product decision extending `ADR-009` onto a new axis, and a design-doc
line can be edited by anyone, whereas reversing this now requires an ADR that argues against
`ADR-009` as well. That friction is the point. (The rule should be summarised in `DESIGN.md` too;
this record is the authority.)

## Consequences

**Positive**

- The obvious feature request has a documented answer, and reversing it costs an ADR that must also
  engage with `ADR-009`.
- `RideFacts`'s signature makes the violation unrepresentable rather than merely discouraged.
- Return stays reflective, which is what `docs/PRODUCT.md` describes it as.

**Negative**

- **Riders will ask for this**, and the answer will read as withholding. "Show me my longest ride" is
  a reasonable request that this record refuses.
- **The line is not perfectly sharp.** A year divider in the archive is an aggregate that ships; a
  lifetime total is an aggregate that does not. Decision §1's test resolves most cases but the
  divider is justified by *purpose* (navigation) rather than by the test, which is a seam someone
  will push on.
- **Data to compute the banned statistics exists in Postgres.** Nothing stops a future contributor —
  or the rider, via any SQL client — from computing them. This record constrains what Horizon shows,
  not what is knowable.
- Enforcement rests on `RideFacts` staying the only component that renders ride statistics. A second
  one, added without reading this, reopens the door quietly.

## Trade-offs

| We gave up | We got |
|---|---|
| The most obvious and most requested feature for a ride archive | A Return register that stays reflective rather than evaluative |
| Lifetime totals, which are genuinely true facts | No mechanic that only goes up and asks to be watched |
| Flexibility to revisit case by case | A mechanical test that resolves the argument without one |

## Future Revisions

Revisit if:

- **`docs/PRODUCT.md`'s No Gamification pillar is itself revised.** That is the only thing this
  record is downstream of; nothing else changes the answer.
- **A second statistics component appears**, which is the failure mode Decision §4 is designed
  against and the signal that enforcement has drifted.

**What would *not* justify revisiting:** riders asking for personal bests, or an argument that a
particular total is "just a fact." Both are anticipated here, and both are the decision rather than
an oversight.
