# ADR-021: Location updates run in a task that may execute with no React tree, and a killed process loses fixes rather than buffering them

| | |
|---|---|

## Context

`docs/SYSTEM_DESIGN.md` §11 names background location as Phase 4, and `CLAUDE.md` warns it is *"an
OS-permissions problem … identical on every framework — treat it as Phase 4, not a quick add."*

The permissions half is the well-known half. The half that needs a decision is structural: **the
store and the WebSocket become reachable from a JavaScript context with no React tree.**
`docs/ADR/README.md` lists "changes the concurrency model" as an escalation trigger, and this is
that — `mobile/src/state/useRide.ts`'s module-scope `handle` and the socket it owns are currently
only ever touched from inside a mounted component tree, and after this they are not.

The concrete problem: today `mobile/src/app/ride/[code].tsx` runs
`Location.watchPositionAsync` in a `useEffect`. When Android backgrounds the app, that effect's
delivery stops, and the convoy watches that rider's `ageSec` climb until they grey out — during a
ride the rider is still on. Screen-off is the normal state of a phone in a handlebar mount on a long
straight.

## Decision

### 1. One GPS subscription, not two — the task replaces `watchPositionAsync`

`Location.startLocationUpdatesAsync` with an Android foreground service becomes the *only* source of
fixes, in both foreground and background. The `watchPositionAsync` effect in `ride/[code].tsx` is
deleted, not kept alongside.

This is deliberate and load-bearing. `mobile/src/features/convoy/MapCanvas.tsx`'s own doc comment
records that it refuses MapLibre's `trackUserLocation` specifically to avoid a second GPS
subscription on rides that run for hours; running the task *alongside* the existing watcher would
reintroduce exactly that, with the added confusion of two delivery paths writing the same store
field at different cadences.

The cost is real and should be field-tested first: the foreground path now goes through the task
too, so if task delivery is laggier than `watchPositionAsync` on real hardware, the speedometer and
the camera feel it.

### 2. The task calls the same store action the UI already calls

On Android the JS context normally survives backgrounding — the foreground service keeps the process
alive, so `wsClient.ts`'s socket and `useRide.ts`'s module-scope `handle` are the same objects the UI
was using, and React Native's OkHttp-backed `WebSocket` is not suspended. A foreground service also
exempts the app from Doze network restrictions for its lifetime.

So the background fix reaches the socket by the most boring path available:
`useRide.getState().sendLoc(fix)`. No bridge, no queue, no new mechanism. `sendLoc` already sets
`ownFix` before forwarding and is already throttled to ~1 Hz by `MIN_LOC_INTERVAL_MS`, and since
`ADR-018` it also folds the fix into the ride-track accumulator — which means **a backgrounded ride
still records its distance and track**, rather than producing a Return summary with a hole in it.

### 3. `defineTask` runs at module scope

Not in a hook, not in an effect. The task must be registered on **every** JS context creation,
including a headless restart where React never mounts. This is the single easiest thing to get
wrong, because it works fine in every test where the app was already open.

### 4. A headless restart rejoins from persisted session; it does not buffer

The case where the JS context does *not* survive: the OS kills the process under memory pressure or
a user swipe-away, then later restarts it **headless** to deliver a location update. Fresh context,
no React tree, `handle === null`, `useRide.getState().code === null`.

The task handles it by rejoining: read the persisted ride code and rider name from AsyncStorage, call
`join()`, then send. Everything needed already exists — `riderName.ts`, `join()`, and since
`ADR-017` a Supabase session that also lives in AsyncStorage and yields a token without a UI. It
needs one new persisted value (the ride code) and about ten lines.

Because Android runs the headless task in the same runtime the UI later mounts into,
`ride/[code].tsx`'s existing self-connect effect then sees `code === code` and skips — **the headless
socket is simply adopted.** No second connection, no ghost rider.

**Explicitly not built: a store-and-forward buffer of fixes missed during a process death.** Fixes
lost are lost. Backfilling them would need a new WebSocket message type and a "here is where I was
30 seconds ago" semantic on a protocol that is deliberately lossy — the hub broadcasts a snapshot at
4 Hz and has never promised delivery of any individual `loc`. The convoy already sees that rider's
`ageSec` climb and grey out, which is the honest representation of "we do not know where they are,"
and is already implemented.

### 5. The foreground-service notification is not a notification in the sense the product bans

`CLAUDE.md`'s Do/Don't says *"Don't add a notification, badge, count, or ranking."* This one is
unavoidable — Android does not start a foreground service without it — and it is a different kind of
object: an **OS-mandated service indicator**, carrying no badge, no count, no action, and generated
by the platform rather than by Horizon deciding the rider should be told something.

It also does real work for the rider: it is the privacy affordance that says their location is
currently being used. Keep the text plain ("Horizon" / "Sharing your position with your ride."), and
note that removing it is not an option the platform offers.

### 6. Two independent stop paths, because a zombie service is the worst outcome here

`stopBackgroundLocation()` on unmount of the Motion screen, **and** the task self-stopping when it
finds no persisted session. Either alone leaves a failure mode: unmount can be skipped by a process
kill, and the self-stop only runs if a fix is delivered.

A persistent "Horizon is using your location" notification with no ride behind it is the worst bug
this feature can ship — it is a battery drain and a privacy alarm at the same time, and the rider's
only recourse is to force-stop the app.

Relatedly, `leave()` must clear the persisted ride code, or a headless restart days later rejoins a
long-GC'd room, gets `rejected`, and burns battery retrying. Note the ordering trap `riderId.ts`
already documented for the rider name: `join()` calls `leave()` first, so a fire-and-forget clear can
land *after* the save.

### 7. `app.config.ts` needs no change

It was written ahead of this phase: `expo-location` already carries
`isAndroidBackgroundLocationEnabled: true` and `isAndroidForegroundServiceEnabled: true` — which is
what emits `ACCESS_BACKGROUND_LOCATION`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION` and the
API-34-mandatory `foregroundServiceType="location"` — and iOS already declares
`UIBackgroundModes: ["location", "audio"]`. `expo-task-manager` has no config plugin and is
autolinked.

Verify that against the SDK 56 docs before trusting it; `mobile/AGENTS.md` exists precisely because
this API surface moves.

### 8. Background permission is requested in Departure, once, never mid-ride

Android requires foreground location to be granted before background can be requested, and
`ACCESS_BACKGROUND_LOCATION` must be requested separately (Android 11+ sends the user to Settings).
`mobile/src/app/index.tsx` already requests foreground; background joins it there, framed as what it
actually does — keeps sharing your position when the screen is off.

Denial is not fatal. Without it the service still runs while the app is foregrounded, which is
exactly today's behaviour, so the feature degrades to the status quo rather than breaking.

## Alternatives Considered

### Keep `watchPositionAsync` for the foreground and add the task only for the background

Avoids the risk in Decision §1 entirely — the foreground path stays on the code that is already
known to work, and the task is purely additive. **Rejected:** it is two GPS subscriptions on a
multi-hour ride, which is the exact cost `MapCanvas.tsx` already refuses `trackUserLocation` to
avoid, and it creates two delivery paths writing `ownFix` at different cadences with a handover at
backgrounding — a race with no clean place to arbitrate it.

### Buffer missed fixes and backfill on reconnect

No data loss, and a Return summary with no gap in its track. **Rejected** per Decision §4: it needs a
new WS message type and a backfill semantic on a protocol that is lossy by design, to fix a gap the
`ageSec` mechanism already represents honestly. Worth reconsidering only if the *track* (rather than
the live convoy view) turns out to have unacceptable holes — and even then the fix is local
accumulation, not a protocol change, since `ADR-018`'s accumulator runs on the same fixes.

### Push a position from the native side and skip the JS context entirely

Robust against every JS-context failure mode, and how a native app would do it. **Rejected** as a
large amount of platform-specific native code — in a project whose client is deliberately all
React Native — to handle a case the rejoin path in Decision §4 covers in about ten lines.

### Deferred/batched location updates to save battery

`deferredUpdatesInterval` would let Android batch fixes and wake the app less often. **Rejected:** a
convoy needs live positions, and a batched update that arrives 30 seconds late is worse than useless
— it would be presented as current. `ageSec` exists precisely so stale data is never shown as live,
and deliberately introducing staleness fights it.

## Consequences

**Positive**

- A ride survives the screen going off, which is the normal state of a phone on a long straight.
- A backgrounded ride still accumulates distance and track for the Return register (`ADR-018`), so a
  summary no longer has a hole where the rider pocketed the phone.
- One GPS subscription, one delivery path, one place that writes `ownFix`.
- A headless restart adopts cleanly into the UI's self-connect, so there is no second connection to
  reconcile.
- `app.config.ts` needs no change and no permission surprise.

**Negative**

- **The store and the socket are now mutated from a context with no React tree.** That is the
  concurrency change this record exists for. Nothing in `useRide.ts` assumes a component tree today,
  but nothing enforces that either, and a future addition that reaches for a hook or a navigation
  call inside the store would break only in the headless case — the hardest one to reproduce.
- **The foreground path is now the task's path.** If delivery is laggier than `watchPositionAsync` on
  real hardware, the speedometer and camera feel it. This is the first thing to field-test.
- **JS timer throttling in the background is an open risk.** `wsClient.ts`'s reconnect is
  `setTimeout`-driven; if Android throttles or pauses JS timers while backgrounded, a mid-ride drop
  might never reconnect and the rider goes silently stale. The fix, if it materialises, is to nudge
  reconnection from inside the location task — which is driven natively at ~1 Hz — rather than from a
  timer. Not built pre-emptively, but recorded so the diagnosis is not started from scratch.
- **Fixes are lost across a process death**, by choice (Decision §4).
- **OEM battery managers kill foreground services** regardless of the platform contract. Unfixable in
  code; the rejoin path is the mitigation.
- **Battery is now at its worst case**: continuous high-accuracy GPS, a keep-awake lock, a
  continuously subscribed WebRTC room (`ADR-020`), and a foreground service. Still unmeasured, as
  `ADR-005` already noted for its share of it.

## Trade-offs

| We gave up | We got |
|---|---|
| A foreground path that was known to work | One GPS subscription instead of two, and no handover race |
| Fixes recorded during a process death | No new WS message type on a protocol that is lossy by design |
| A guarantee that the store is only touched from React | A ride that survives the screen going off |
| Batched updates and the battery they would save | Positions that are live, never stale-presented-as-current |

## Future Revisions

Revisit if:

- **Task delivery proves laggier than `watchPositionAsync`** in the foreground, which would force
  reconsidering Decision §1's single-subscription rule.
- **Background JS timer throttling breaks reconnection**, per the Consequences note — the answer is
  nudging from the task, not a longer backoff.
- **Return summaries show unacceptable holes** in the track after process deaths, which argues for
  local accumulation across restarts rather than the rejected protocol backfill.
- **iOS lands.** Everything here is Android-shaped (`ADR-007`); iOS "Always" permission and its
  background execution model are a different problem wearing the same name.

**What would *not* justify revisiting:** wanting missed fixes backfilled so the live convoy view has
no gaps. `ageSec` greying is the honest representation and it already works.
