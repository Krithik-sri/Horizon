# ADR-018: The rider's phone writes the durable ride record — no Edge Function, and no shared convoy record

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-10 |
| **Deciders** | Horizon team |
| **Supersedes** | — |
| **Amends** | — (resolves a question [ADR-008](./ADR-008.md) left open: it assigned durable state to Supabase without naming who writes it) |

## Context

`ADR-008` split the backends by lifetime and was explicit that the Go server "never touches
Postgres — no DB driver in `go.mod`." That remains true. What it never said is **which actor writes
a durable ride record when a ride ends**, because at the time nothing durable existed to write.

The Return register changes that. A finished ride has facts worth keeping — where it went, how far,
how long, who was there — and something has to insert the row.

## Decision

### 1. The rider's own device writes its own ride record, directly to Supabase

Five reasons, in increasing order of weight:

1. **The Go server cannot.** `ADR-008` forbids a DB driver in `go.mod`, and that constraint is load
   bearing, not incidental.
2. **`SYSTEM_DESIGN.md` §12 already commits to the enforcement model** — *"enforce that with
   Row-Level Security, not application logic."* A client write with RLS is that design; a
   server-side write is the application logic it rules out.
3. **An Edge Function would have to be told the ride ended.** Either by the Go server — which then
   needs a Supabase URL, a service key and an HTTP client, keeping the letter of `ADR-008` while
   breaking its spirit — or by the client, in which case it is a pass-through adding a hop, a cold
   start, and a deploy target to do validation RLS already does.
4. **Client-writes moves no computation.** `docs/ADR/README.md` lists moving work between client and
   server as an ADR trigger; this record moves nothing, because the work is already on the phone.
   The Edge Function is the option that would need justifying.
5. **The truthful data only exists on the phone.** Distance and duration come from that phone's own
   GPS trace. The Go server has never persisted a coordinate (`SYSTEM_DESIGN.md` §12) and by design
   cannot reconstruct one. A server-side writer would be inventing a record it does not have the
   inputs for.

### 2. There is no shared convoy record — each rider's row is their own

Two riders on the same ride produce two independent rows. There is no join, no shared ride object,
no cross-user visibility.

This follows directly from `SYSTEM_DESIGN.md` §1's non-goal — *"a social graph beyond what Supabase
Auth needs"* — rather than from laziness. A shared record needs cross-user reads, which needs a
consent model, which is the social graph the product has ruled out. Companions are stored as a
`jsonb` snapshot on the rider's own row: **who this rider saw, owned by this rider, invisible to
everyone else.**

### 3. The pending-row guard is not optional

The app being killed between "end ride" and the insert — crash, flat battery, no signal at the
roadside — would lose the ride. The mitigation is small and must exist: write a pending row to
AsyncStorage **on ride start**, update it as the ride progresses, promote it to Supabase on end, and
clear it on success. Any launch that finds a pending row promotes it first.

Roughly twenty lines, no queue library, no retry framework. This is error handling that prevents
data loss, which is explicitly not the kind of thing to simplify away — and writing on *start*
rather than on *end* is the whole point, since the failure being guarded against is the one where
"end" never runs.

### 4. Three tables, three deliberate omissions

`rides`, `route_plans`, `ride_photos`, plus a private `ride-photos` Storage bucket. Every table gets
the same four RLS policies keyed on `(select auth.uid()) = user_id` — the parenthesised form, which
Supabase documents as evaluated once per query rather than once per row.

Each omission has a named trigger for reversing it:

- **No PostGIS.** `track` is `jsonb`. Nothing does geospatial querying, and the column is only ever
  read whole. Add it when "rides near this point" is a feature.
- **No `journal_entries` table** — a `note text` column on `rides`. One reflective note per ride is
  what a ride journal is; a table would add a join, a second policy set and orphan risk for nothing.
  Promote when *timestamped moments during a ride* ship, which is a different feature.
- **No `ride_participants` table** — `companions jsonb`, per Decision §2. Promote when a consent
  model exists, which is an ADR, not a migration.

`ride_photos` **is** a table rather than bare Storage listing, against the same instinct, because
`list()` has no ordering guarantee beyond object name and nowhere to put a caption or the
coordinates a photo was taken at — both named in `docs/PRODUCT.md`'s description of Return.

No `is_anonymous` restriction anywhere. An anonymous rider is a full rider (`ADR-016`).

## Alternatives Considered

### A Supabase Edge Function writes the record

Real upsides: one place to change the write shape, server-side validation that does not depend on
every client being up to date, and the ability to write a *shared* ride record visible to all
participants. **Rejected** on Decision §1.3 and §1.5 — it still has to be told the ride ended by one
of the two parties, and it does not have the GPS trace that makes the record true.

### The Go server calls Supabase over HTTP when a room is garbage-collected

Genuinely attractive because it has the one thing the client lacks: a single, reliable trigger point
that fires whether or not any particular phone survived the ride. **Rejected** because it needs a
service key in the Go server — which then holds credentials that bypass RLS for every user — and
because room GC is not ride end. A room is collected five minutes after the last rider leaves, which
says nothing about whether anyone completed a ride.

### One shared ride row per convoy, written by whoever ends first

Matches how riders think about a group ride, and would let the Return register show a genuinely
shared memory. **Rejected** per Decision §2: it requires cross-user reads and therefore consent,
which is out of scope. Worth reopening if the product ever adopts a consent model — this is the most
likely of these to come back.

### Skip the pending row; write only on ride end

Simpler, and the failure window is a few hundred milliseconds. **Rejected** — the window is not the
few hundred milliseconds around the insert, it is the entire ride, because the data being lost was
accumulating the whole time. A flat battery at the far end of a day ride is the exact case Return
exists to serve.

## Consequences

**Positive**

- `ADR-008`'s "no DB driver in Go" constraint holds untouched, and no new server-side component
  exists to deploy or operate.
- RLS is the only access-control mechanism, matching `SYSTEM_DESIGN.md` §12 rather than adding a
  second one.
- A ride survives a crash or a flat battery, because the record is built incrementally rather than
  at the end.
- No consent model needed, because nothing crosses between users.

**Negative**

- **The same ride is stored N times for N riders**, with slightly different distances and durations
  depending on each phone's GPS. There is no canonical version, and two riders comparing numbers
  afterward will find they disagree.
- **Deleting a ride cascades the `ride_photos` row but not the Storage object.** `deleteRide` removes
  objects first, then the row; a kill in between leaves an orphaned object — invisible, and costing
  bytes against the 1 GB free tier. Acceptable; a scheduled sweep only if it bites.
- **Client-side validation is the only validation before RLS.** A buggy client can write a nonsense
  distance to its own row. RLS guarantees isolation, not correctness — the `check` constraints in
  the schema are doing what they can, and they are not much.
- **Photos are what will fill the 1 GB Storage tier**, not tracks. A 300 km ride decimated to one
  point per ~50 m is a few hundred KB of `jsonb`; a handful of full-resolution photos is more.
  Client-side resizing before upload is not optional at any real usage.

## Trade-offs

| We gave up | We got |
|---|---|
| A canonical, shared record of a group ride | No consent model, no cross-user reads, no social graph |
| Server-side validation of durable writes | No Edge Function to deploy, no service key anywhere, `ADR-008` intact |
| A single reliable trigger point for "the ride ended" | A record built from the only data that is actually true — the phone's own trace |
| Simplicity of writing once, at the end | A ride that survives the crash it was most likely to be lost to |

## Future Revisions

Revisit if:

- **A consent model ships**, at which point the shared-convoy-record alternative becomes available
  and `ride_participants` becomes a real table.
- **Timestamped moments during a ride ship**, which promotes `note` to a `journal_entries` table.
- **Geospatial querying is wanted** ("rides near here"), which is when PostGIS earns its place.
- **Storage orphans accumulate** enough to matter, per the cleanup note above.

**What would *not* justify revisiting:** wanting server-side validation for its own sake. RLS
enforces the boundary that matters — a rider can only write their own rows — and correctness of a
rider's own distance figure is not a security property.
