# ADR-014: Off-route rerouting is personal — a rider's wrong turn never changes the convoy's route

| | |

| **Status** | Accepted |
| **Date** | 2026-08-10 |
| **Deciders** | Horizon team |
| **Supersedes** | — |
| **Amends** | [ADR-012](./ADR-012.md) (Decision §4 → "Off-route rerouting and spoken guidance remain excluded": narrows that list from two items to one — rerouting moves in scope, spoken guidance stays excluded pending its own record) · [ADR-011](./ADR-011.md) (Decision → "Explicitly still out of scope", same narrowing) — neither is superseded |

## Context

`ADR-012` closed the door on rerouting deliberately and gave its reasons:

> "**Detection is not permission to reroute.** Automatically re-calling ORS when a rider drifts off
> the stored line is a separate decision with its own quota question (a rider who's genuinely
> off-route could trigger far more than the 'handful of route changes' `ADR-011`'s quota math
> assumed) and its own behavior question (how far off, for how long, before a reroute fires — and
> whether it fires silently or asks)." (`ADR-012`, Decision §4)

It also listed, under Negative consequences, the exact hazard this record has to avoid becoming:

> "`routeProgress.ts`'s off-route detection is now sitting in the app, unused for rerouting. That
> remains … an obvious invitation to wire up automatic rerouting next."

The repo owner has approved building rerouting. This record exists because approval is not an
answer to either question `ADR-012` raised — so both are answered below with numbers, not vibes.
Unlike `ADR-012`, which named itself a postmortem, this is written before the code.

There is a third question `ADR-012` did not ask, and it turns out to be the one that shapes the
design. Horizon is not a single-rider navigation app. `backend/internal/hub/room.go` stores one
`routeMsg` per room and fans it out to everyone; `ADR-011` established that as "one *stored* route
per ride, replaceable." So "reroute the rider" and "reroute the route" are the same action under the
current model — **which means the naive implementation lets any one rider's wrong turn redraw the
line for the entire convoy.** A follower who misses an exit would drag five other riders onto a
detour they can see out their windscreen is wrong. That failure is worse than no rerouting at all.

## Decision

### 1. A reroute is personal — fetched by one rider, rendered on one device, never broadcast

The off-route rider fetches their own route and holds it in their own store. `hub.SetRoute` is never
called. No `route` frame is emitted. No other rider learns it happened.

The convoy's stored route is therefore **immutable with respect to any rider going off-route, by
construction** — not by a rule someone has to remember, but because the code path that would change
it is not on this feature's path at all.

The Motion screen renders `activeRoute = rejoin ?? route`. Everything downstream — the maneuver cue,
the ETA readout from `ADR-013`'s phase, progress matching — operates on `activeRoute` and needs no
knowledge that a detour is in play.

### 2. It reuses `ADR-013`'s `preview` flag — no new endpoint

`POST /rides/{code}/route` with `preview: true` already means exactly this: *fetch a route, return it
to this caller, store nothing, broadcast nothing.* `ADR-013` Decision §1 said the mechanism was meant
to generalize and that the next such feature should reach for the flag rather than add an endpoint.
This is that next feature, and it does.

Worth recording against `ADR-013`'s Future Revisions note — *"if the `preview` flag starts carrying
unrelated meanings, that is the signal to split it"* — that the meaning here is **not** new. A
planner preview and a personal detour are the same thing: a route that belongs to one screen rather
than to the room. The flag has one meaning and now two callers.

An un-scoped `POST /route` was reconsidered here on the grounds that a detour is even less
ride-specific than a preview. It was rejected again, for `ADR-013` Decision §1's reason plus one
more: an endpoint that needs no ride code has nothing gating it at all, and the reroute path is
automatic — it fires without a rider tapping anything, which is precisely the traffic you do not
want on an ungated ORS proxy.

### 3. The personal route targets the destination, not a rejoin point

The obvious design is to route the rider back to a chosen point on the shared polyline. This record
routes them to the **final destination** (`route.polyline[len-1]`) instead. Three reasons, in
increasing order of weight:

- **No heuristic to tune.** "Which vertex do I aim for" has no good answer. The nearest vertex is
  frequently *behind* the rider; "the nearest vertex 500 m ahead" is a guess with a magic number
  inside it, and it is wrong in different ways on a motorway than in a town.
- **ORS is better at this than a heuristic would be.** Given the current fix and the destination, the
  same optimizer with the same cost function decides whether the right move is a U-turn, the next
  exit, or a parallel road. In practice it rejoins the convoy's road within a kilometre because that
  road was already optimal.
- **It needs no auto-clear.** This is the one that decided it. A rejoin-point route has to be
  detected as "completed" and discarded, which means a second `computeProgress` pass, a second
  anchor, and a rule for what happens if the rider goes off the *rejoin* route. A
  destination-targeted route simply converges: once the rider is back on the group's road the two
  polylines describe the same line, and there is nothing to clear.

It also means the detour carries its own `steps` and `summary`, so the maneuver cue and ETA keep
working across it with zero additional code.

### 4. The trigger contract

All five conditions required. The first two answer `ADR-012`'s behaviour question; the last three
answer its quota question.

| Condition | Value | Why this one |
|---|---|---|
| Consecutive off-route fixes | **5** (~5 s at the 1 Hz GPS rate) | One bad fix under a bridge is not a missed turn |
| Distance from the line | **≥ 120 m** | `OFF_ROUTE_METERS = 50` already means "don't assert a turn." 120 m means "different road." Two thresholds for two different questions beats one threshold doing both badly |
| Speed | **≥ 2 m/s** | A bike parked 60 m off the line at a petrol stop must never spend a request |
| Cooldown | **60 s** since the last attempt, success or failure | Caps one rider at 1 request/minute |
| Attempts per stored route | **5**, reset by every incoming `route` frame | A genuinely lost rider cannot grind the quota; resetting on a new shared route is naturally correct because it is a new problem |

**The quota arithmetic `ADR-012` asked for, explicitly.** Worst case is 5 requests per rider per
destination. A six-rider convoy where every rider gets lost on every leg spends ~30 requests — 1.5%
of the 2,000/day ceiling. Against the tighter 40/minute limit, the 60 s cooldown bounds that same
convoy at 6 requests/minute, leaving room for the geocode and preview traffic `ADR-012` and `ADR-013`
already put on the same account. The honest summary: rerouting is not what will exhaust this quota.
`ADR-013`'s previews are.

### 5. When the cap is hit, the feature degrades rather than failing

Past 5 attempts, or on any error, the maneuver cue keeps reading "Off route" and gains a **bearing
and distance to the nearest point on the route**, computed entirely from values already in
`Progress`. Zero requests, no network, works with the quota fully exhausted.

This is the floor the feature never drops below, and it matters more than the reroute itself: it
means "lost with no data" is a supported state rather than a blank screen.

### 6. Rendering: dashed, in the existing accent

The personal route draws in `amber.core` with a dash pattern. The convoy's route stays drawn beneath
it, forced to `amber.dim` for as long as a detour is active, so the rider can always see the line
they are trying to get back to.

Dash is *texture*, not hue. `docs/DESIGN.md` §1's one-accent rule and `ADR-012` §3's brightness-not-
colour decision both stand untouched, and the dash carries a specific meaning worth having: **this
line is yours alone.** No other rider is seeing it.

### 7. No WebSocket protocol change

Stated explicitly so a future reader does not go looking for one. `loc`, `welcome`, `state` and
`route` are all unchanged, as are `hub.SetRoute` and `Room.routeMsg`.

## Alternatives Considered

### Only the rider who set the destination reroutes; everyone converges via the `route` frame

Genuinely attractive: no new client state, no new rendering, one line on every screen, and the
convoy stays visually unified — which is most of what a convoy feature is for. **Rejected** because
it fails in the common case and the uncommon case for opposite reasons. The rider who misses a turn
is usually a *follower*, not the person who set the destination — they would get nothing at all. And
on the occasions when the route-setter is the one who missed it, the entire convoy's line changes to
accommodate one rider's error, which is the failure named in Context.

### The Go server detects off-route and reroutes once for the group

The hub already receives every rider's position at 4 Hz, so detection would need no new data, and
there would be exactly one place where rerouting logic lives instead of one per device. **Rejected**
on four counts, any one of which would be sufficient: it moves a computation from client to server,
which `docs/ADR/README.md` lists as its own ADR trigger; it requires reimplementing
`mobile/src/core/routeProgress.ts`'s polyline matching in Go and keeping two copies in agreement; it
runs per-rider geometry inside the single `Hub.mu` that `ADR-010` deliberately kept simple, at
broadcast rate; and — decisively — it still produces *one shared route*, so it costs the most of any
option on the table and does not solve the problem the others are being judged against.

### Personal reroute, plus telling the convoy that a rider is off-route

The safety argument for this is real and should not be dismissed: a group riding together generally
wants to know when someone has dropped off. **Rejected** because "Sam is off route" is a
notification, and `CLAUDE.md`'s Do/Don't forbids notifications outright — a rule that traces back to
`docs/PRODUCT.md`'s "not a notification machine." The information is also already present in a form
the product does allow: a rider who has diverged appears at a diverging position on everyone's map,
and `ageSec` greying already covers the case where they drop off the network entirely. If this needs
revisiting it is a `horizon-design` question about the convoy display, not a rerouting question.

### Route to a rejoin point on the shared polyline instead of the destination

Covered in Decision §3. Its real upside is that the rider provably returns to the *group's* line
rather than to a possibly-different road that merely ends in the same place. Rejected for the
heuristic tuning and the auto-clear state machine it requires.

### Ask before rerouting

`ADR-012` explicitly raised this as an open question — "whether it fires silently or asks."
**Rejected:** a prompt is an interruption, delivered to a rider who by definition is currently
confused about where they are, at a moment when they may well be in traffic looking for a place to
turn around. `docs/PRODUCT.md`'s corner rule and the Attention Ladder both point the same way.
Rerouting silently and letting the ambient cue's content change is consistent with `ADR-012` §2's
whole construction: no delivery event, nothing that can land at a bad moment.

## Consequences

**Positive**

- One rider's wrong turn provably cannot change what the rest of the convoy sees.
- No protocol change, no new endpoint, no hub change — the feature is client state plus a flag that
  already existed.
- ETA and maneuver cues work unmodified across a detour, because the personal route carries its own
  `steps` and `summary`.
- A genuine floor exists when the quota is gone (Decision §5), so "lost" is never a blank screen.
- `ADR-012`'s standing invitation — off-route detection sitting unused — is now answered on the
  record instead of being taken up silently.

**Negative**

- **A convoy that diverges together produces N divergent personal routes.** If the group collectively
  takes a scenic detour, every rider reroutes independently within seconds and they may navigate
  slightly different lines toward the same destination. The dimmed shared route is the only thing
  holding them together visually; the rest is a conversation, i.e. `ADR-005`'s voice channel.
- **The personal route may not retrace the group's road.** Decision §3 accepts this in exchange for
  deleting the auto-clear machinery. A rider could rejoin the destination by a different road than
  the convoy takes and never notice.
- **Urban-canyon GPS error can exceed 120 m.** The 5-fix and speed gates catch most of it and the
  cooldown caps the cost of the rest, but a false reroute in a city centre is possible and will look
  like a bug to the rider.
- **One more piece of client state Motion must reconcile.** `activeRoute = rejoin ?? route` is a
  small expression, but it is a second answer to "what route am I on," and the codebase has so far
  been disciplined about having exactly one.
- **Automatic ORS traffic now exists.** Every prior request was the direct result of a rider tapping
  something. This is the first that fires on its own, which changes the risk profile of the
  unauthenticated route endpoint — the per-IP rate limiter `backend/main.go`'s middleware comment
  already reserves a slot for is now overdue rather than hypothetical.

## Trade-offs

| We gave up | We got |
|---|---|
| One route line shared by the whole convoy | A convoy route that one rider's mistake cannot rewrite |
| A provable return to the group's exact road | No rejoin heuristic, no auto-clear state machine, and a detour that carries working cues and ETA for free |
| A shared, server-side view of who is lost | No notification, and no computation moved into the hub |
| Confirmation before rerouting | No interruption delivered to a rider who is already confused |
| Unlimited retries for a genuinely lost rider | A quota ceiling that a lost convoy cannot grind through, and a zero-request degraded mode underneath it |

## Future Revisions

Revisit if:

- **Riders report the personal route peeling away from the group's road.** Rejoin-point targeting is
  the answer, and Decision §3's reasoning would need re-examining against field data rather than
  against the tuning argument made here.
- **The 5-attempts-per-route cap is hit during normal riding.** That means the thresholds are wrong,
  not that the cap is — retune before removing.
- **False reroutes in cities prove common.** The next lever is requiring the 5 off-route fixes to be
  *increasingly* distant rather than merely all beyond 120 m, which distinguishes drift from GPS
  scatter without a new sensor.
- **The route endpoint is abused.** This record is what makes the rate limiter overdue.
- **Spoken guidance ships.** It is still excluded, and still needs its own ADR — this record narrows
  `ADR-012` §4 by exactly one item and no more.

**What would *not* justify revisiting:** wanting the reroute broadcast to the convoy so everyone sees
one line. That is the decision, not an omission — Decision §1 and the first two rejected alternatives
all exist to record it.
