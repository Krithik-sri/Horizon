## Context

`ADR-011` named navigation a first-class Horizon capability but was explicit about the boundary:

> "Explicitly still out of scope, and not decided by this ADR: off-route rerouting, spoken audio
> guidance, and destination search (geocoding)." (`ADR-011`:47–48)

It also left a second question open on the record, this time about *how* a maneuver cue is allowed
to reach the rider at all:

> "how maneuver cues are surfaced without violating the corner rule is a `horizon-design` decision
> this record deliberately leaves open." (`ADR-011`:197–198)

Neither question waited for an ADR. Commit `e93a191` ("feat: implement geocoding functionality
with search and result handling", 2026-08-08) added `POST /geocode` (`backend/geocode.go`, an ORS
Pelias proxy via `backend/internal/ors/geocode.go`), `mobile/src/core/geocode.ts`, and a search flow
in Departure — first inline in `mobile/src/app/index.tsx`, since factored into
`mobile/src/features/departure/DestinationSearch.tsx`. `POST /geocode` is now documented in
`CLAUDE.md`'s HTTP surface alongside the other endpoints. In the same span of work, the maneuver cue
(`mobile/src/features/motion/AheadCue.tsx`) was rebuilt as a single persistent element and the route
line (`mobile/src/features/convoy/RouteLine.tsx`) was rebuilt to draw two-tone. `docs/SYSTEM_DESIGN.md`
still listed destination search under non-goals at the time this ADR was written: *"Off-route
rerouting, spoken guidance, and destination search — not yet decided ([`ADR-011`](./ADR/ADR-011.md))."*
(`docs/SYSTEM_DESIGN.md`:34–35, before this ADR's doc pass).

Per `docs/ADR/README.md` rule 4 — *"Write it before the code, not after. An ADR justifying a merged
PR is a postmortem."* — this is a postmortem, and it says so plainly rather than presenting the
sequence as if the ADR came first. The repo owner has confirmed the destination-search decision
after the fact; this record exists to make that decision legible, correct the two stale documents
it left behind, and put a boundary back around what is still not decided.

## Decision

### 1. Destination search (geocoding) is in scope

A rider cannot realistically choose a destination by long-pressing a dark map at a petrol stop.
Destination search closes that gap. It is scoped narrowly:

- **Same free key, no new constraint.** ORS's Pelias geocoder sits behind the same no-card,
  email-signup-only ORS account `ADR-003` and `ADR-011` already use for `driving-car` directions —
  `CLAUDE.md` hard constraint #1 holds unchanged; this is not a new third-party dependency.
- **`POST /geocode`, not `GET /geocode?q=...`.** `backend/geocode.go`'s handler comment and
  `CLAUDE.md`'s HTTP-surface section both give the same reason: a searched destination is location
  data — the most sensitive class this app handles — and a GET endpoint would put that text in a
  query string. For the record, verified against the current code rather than repeated on faith:
  `backend/internal/httpx/logging.go`'s own doc comment says it deliberately logs `r.URL.Path` only,
  never `r.URL.RawQuery` — so today's structured application log specifically would not have
  captured a query string either way. The POST choice is still correct: a URL is visible to browser
  history, intermediate proxies, and edge/CDN logs in a way a POST body is not, so POST closes the
  whole class of exposure rather than depending on one log line staying scrubbed. The identical claim
  about `internal/httpx/logging.go` in `ADR-008`'s Decision section (for the WS bearer token) has the
  same gap between claim and current code and is worth reconciling the next time either file changes
  — noted here, not fixed here, since neither `ADR-008` nor `logging.go` is this record's to edit.
- **Departure only.** `DestinationSearch.tsx` is mounted only from `mobile/src/app/index.tsx`'s
  start-a-ride and join-a-ride flows. `mobile/src/app/ride/[code].tsx` — the Motion screen — has no
  search UI and no `geocode.ts` import; it sets a destination only via a map long-press
  (`handleLongPress` → `setDestination`), which needs no text entry at all. A text keyboard while
  moving is against the Motion register (`horizon-design` §5, §1); search staying Departure-only is
  not an oversight, it's the constraint holding.

**Narrowing `ADR-011`, not correcting it.** `ADR-011`'s "explicitly still out of scope" list (quoted
above) was accurate when written — this isn't a wrong claim like the ones `ADR-011` itself fixed in
`ADR-003`/`ADR-006`. It's a boundary this record moves. `ADR-011`'s list named destination search
alongside rerouting and spoken guidance; that's narrowed by this record:
destination search is in scope; rerouting and spoken guidance are not (see §4). `ADR-011` is not
superseded — its `route` message protocol, the correction to `ADR-003`/`ADR-006`, and the "once per
stored route" relaxation are untouched by this decision.

### 2. The Attention Ladder rung for maneuver cues: ambient, not eventful

The decision taken: **the cue is persistent and ambient.** Exactly one element occupies the Ahead
band whenever a route is set; only its *content* changes. `AheadCue.tsx`'s own doc comment states
the mechanism this record is ratifying: every branch renders *something* in the same card rather
than mounting or unmounting it, so "nothing here ever appears, slides, flashes, or pulses into the
rider's field of view mid-ride."

Nothing about a maneuver cue speaks, vibrates, or otherwise escalates up the Attention Ladder
(`horizon-design` §2) beyond Visual — it sits at Visual, always on, never re-triggered. Because
there is no delivery *event*, there is nothing that can land mid-corner: **the "never interrupt a
corner" rule is satisfied by construction**, not by trying to detect lean or a turn in progress,
which the app has no sensor for and was never going to get one for free.

The honest cost, recorded rather than glossed over: **a maneuver cue can be missed.** A rider who
doesn't glance at the Ahead band at the right moment gets nothing louder to catch their attention —
by design, since anything louder is either an interruption (ruled out by the corner rule for
non-safety information) or a new delivery event (reopening the exact timing problem this decision
closes). The design accepts a missed glance over risking an interruption mid-lean.

### 3. Two-tone route line, not a second accent

`docs/DESIGN.md` §1 is explicit: *"There is one accent. Amber. A second accent hue needs an ADR."*
A blue, Google-Maps-style route line was considered for exactly the reason those lines are
conventional — high contrast against a dark map, an unambiguous "this is the route, that is the
rider" split — and rejected on that rule: it's a second accent hue, and this record is not spending
its decision budget there.

Instead `RouteLine.tsx` draws the full route in `amber.dim` with the un-ridden remainder redrawn on
top in `amber.core`, so brightness — not hue — encodes "still ahead of you." One accent, doing two
jobs by intensity rather than by adding a color. That is meaning, not decoration, in the same sense
`docs/DESIGN.md`'s "color communicates meaning" rule already requires.

The side benefit is worth recording on its own: before this, `amber.core` simultaneously meant the
route, the rider marker, "active," and `signal.caution` (`docs/DESIGN.md` §1 — caution and
`amber.core` are deliberately the same value). Dimming the ridden portion of the route to `amber.dim`
relieves `amber.core` of carrying "the whole route" on top of everything else it already signals.

### 4. Off-route rerouting and spoken guidance remain excluded

Unchanged from `ADR-011`. `mobile/src/core/routeProgress.ts` now *detects* off-route
(`OFF_ROUTE_METERS`, the `onRoute` field on `Progress`) as a side effect of matching a rider's fix to
the polyline for the maneuver cue above. **Detection is not permission to reroute.** Automatically
re-calling ORS when a rider drifts off the stored line is a separate decision with its own quota
question (a rider who's genuinely off-route could trigger far more than the "handful of route
changes" `ADR-011`'s quota math assumed) and its own behavior question (how far off, for how long,
before a reroute fires — and whether it fires silently or asks). Spoken audio guidance is excluded
for the reason `ADR-011` already gave: it is a `horizon-design`-scale question, not resolved by
`routeProgress.ts` merely existing. Both need their own ADRs before either ships.

## Alternatives Considered

### Destination search: keep long-press-only, no text search

The narrowest reading of `ADR-011`'s original exclusion — don't add geocoding, live with
long-press. **Rejected:** a long-press only works for a destination visible on the currently loaded
map. A rider planning a ride to a town three hours away, or standing at a petrol stop deciding where
to go next, cannot long-press a place they cannot see. This is the concrete failure `docs/PRODUCT.md`'s
Confidence pillar rules out — *"if information cannot be trusted, it should not be shown"* extends
to "if the rider cannot act, the affordance is not real."

### Destination search: `GET /geocode?q=...`

Simpler, cacheable by intermediate infrastructure, one fewer thing for a client to serialize as a
body. **Rejected** for the location-data-in-a-URL reason given in Decision §1 — the same standing
rule that put the WS bearer token in a header instead of a query string (`ADR-008`).

### Maneuver cues: an event-driven banner that slides/appears near a maneuver

The conventional turn-by-turn pattern — a card slides in as a turn approaches, slides out after.
Attractive: it's the shape every rider already recognizes from other navigation apps, and it can
carry more urgency right when urgency is warranted. **Rejected:** a slide-in is a delivery *event*,
and an event needs a rule for when it's allowed to fire — which means detecting whether the rider is
mid-corner, which needs a sensor this app doesn't have. The ambient design in Decision §2 avoids
needing that sensor at all, by removing the event instead of trying to time it safely.

### Maneuver cues: haptic pulse on an approaching maneuver

Genuinely tempting — haptic sits below Visual on the Attention Ladder (`horizon-design` §2), so it
reads as the more conservative choice, not a louder one. **Rejected for the same reason as the
sliding banner:** a haptic pulse is still a delivery event with a firing moment. Moving the event to
a different channel doesn't remove the timing problem, it just makes the mistimed delivery a buzz
instead of a slide.

### Route line: a second accent (blue) for the un-ridden remainder

Covered in Decision §3 — rejected against `docs/DESIGN.md`'s one-accent rule, in favor of encoding
the same distinction with brightness instead of hue.

## Consequences

**Positive**

- A rider can choose a destination that isn't already visible on the map — the practical gap
  long-press-only navigation left open.
- `docs/SYSTEM_DESIGN.md`'s non-goals list now matches what's actually shipped, instead of silently
  drifting from the code (corrected by this ADR's doc pass).
- The corner rule holds for maneuver cues without needing lean/turn detection the app has no sensor
  for — solved by removing the delivery event, not by adding sensing.
- `amber.core` carries less overloaded meaning now that the ridden portion of the route dims to
  `amber.dim` instead of staying full-bright alongside the rider marker and every other `amber.core`
  use.

**Negative**

- **This is a postmortem ADR.** The code shipped before the decision was written down, which is
  exactly what `docs/ADR/README.md` rule 4 warns against. Naming it here doesn't undo it, but a
  repeat of the same sequence on the next feature is a process problem, not a one-off.
- **A maneuver cue can be missed**, by design (Decision §2). There is no fallback escalation if a
  rider doesn't glance at the Ahead band before a turn — the design's answer to that risk is "don't
  interrupt," not "catch it another way."
- **`routeProgress.ts`'s off-route detection is now sitting in the app, unused for rerouting.** That
  remains, as `ADR-011` already flagged for turn-by-turn generally, an obvious invitation to wire up
  automatic rerouting next. It is explicitly not authorized by this decision (Decision §4).
- **Geocode traffic shares ORS's quota with the route proxy.** Both endpoints run through the same
  free-tier ORS account (2,000 requests/day, 40/minute — `ADR-011`). A search-heavy Departure session
  (a rider trying several queries before picking a destination) now competes with route requests for
  the same ceiling; nothing currently distinguishes the two at the quota level.
- **`ADR-008`'s claim about `internal/httpx/logging.go`** — "logs request URLs" — has the same gap
  against current code as the one this ADR found for geocode (Decision §1). Flagged, not fixed, by
  this record.

## Trade-offs

| We gave up | We got |
|---|---|
| `ADR-011`'s clean boundary — geocoding and rerouting/spoken-guidance grouped together as one deferred bundle | Destination search shipped as its own decision, narrower than the bundle it came out of |
| Writing the ADR before the code (`docs/ADR/README.md` rule 4) | An honest record of the actual sequence, instead of a fictional one |
| A conventional, event-driven maneuver banner | A corner-safety guarantee that holds without a lean sensor, at the cost of cues that can go unseen |
| A second, higher-contrast accent color for the route's un-ridden portion | One accent doing two jobs by brightness, keeping `docs/DESIGN.md`'s one-accent rule intact |

## Future Revisions

Revisit if:

- **Off-route rerouting or spoken guidance are actually built.** Both remain explicitly excluded
  (Decision §4) and each needs its own ADR — this record does not pre-authorize either, regardless
  of how ready `routeProgress.ts`'s detection makes rerouting look.
- **Riders report missing maneuver cues often enough that "ambient only" stops being sufficient.**
  The next lever is likely a haptic pulse tied to `imminent` (already computed in `routeProgress.ts`)
  rather than a visual event — revisit Decision §2's rejected alternatives at that point, since the
  reasoning that ruled them out (timing safety) would need to be re-examined against real field data,
  not just the sensor argument made here.
- **ORS quota pressure becomes real** now that geocode and route-proxy traffic share one account.
  `ADR-003`'s Future Revisions path (cache, then self-host) applies here too.
- **A future contributor needs to reconcile the `internal/httpx/logging.go` claim** in this record
  and in `ADR-008` against what the middleware actually logs — noted twice now, fixed nowhere yet.

**What would *not* justify revisiting:** wanting rerouting or spoken guidance sooner because
detection already exists — that's the invitation this record explicitly declines (Decision §4).
