# ADR-017: `/ws` requires a verified Supabase JWT, and the rider id is the token's `sub`

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-10 |
| **Deciders** | Horizon team |
| **Supersedes** | — |
| **Amends** | [ADR-008](./ADR-008.md) (Decision → JWT verification: not a reversal — this record *implements* what ADR-008 specified, and corrects two documents that described it as already existing) |

## Context

This is a WebSocket protocol change (`docs/ADR/README.md` escalation rule), so it needs a record
regardless. But the more useful thing to write down is that the system it describes was already
documented as real.

`docs/SYSTEM_DESIGN.md` §4 and `CLAUDE.md`'s Architecture section both describe the Go server
verifying Supabase JWTs on the WebSocket upgrade, in the present tense, with the algorithm and env
var named. `ADR-008` describes the same. None of it exists:

- `backend/go.mod` has exactly one dependency, `gorilla/websocket`. There is no `golang-jwt`.
- `hub.ServeWS` reads `?ride=`, `?name=` and `?rider=` and upgrades. There is no auth check anywhere
  in the middleware chain, which is `Recover → Log → CORS → mux`.
- `mobile/src/core/wsClient.ts` carries the comment `// No auth today`.

So three documents assert a security control that has never been implemented. That is worse than
having no control, because it is the kind of thing a reader checks once, believes, and never checks
again. Closing the gap is this record's job; correcting the documents is part of the same work, not
a follow-up.

`ADR-016` establishes that every rider now has a Supabase session. This record is what makes the Go
server care.

## Decision

### 1. One middleware, wrapping the whole mux, failing closed

New leaf package `backend/internal/auth`. `/healthz` is the only public path.

**Wrapping the mux rather than per-route** for the reason `backend/main.go`'s own comment already
gives for CORS — *"so /ws and every route added later inherit the policy without anyone remembering
to."* An authorization boundary is exactly the kind of thing that must cover routes nobody has
written yet; per-route middleware fails open on the one someone forgets.

### 2. The chain becomes `Recover → Log → CORS → Auth → mux`

Position is load-bearing in both directions:

- **Inside CORS**, because a browser preflight carries no `Authorization` header — the browser
  strips it — so auth outside CORS would 401 every `OPTIONS`. CORS answers preflights itself and
  Auth never sees them.
- **Inside Log**, so 401s appear in the access log. An auth boundary whose rejections are invisible
  is not observable.

`internal/httpx/logging.go` logs `r.URL.Path` only and never headers, so the bearer token is not at
risk there. That property is what `ADR-008`'s "never a token in a query string" rule exists to
preserve, and this record keeps it: the token rides in a header, on both the HTTP routes and the WS
upgrade, which native React Native's `WebSocket` supports via its non-standard `headers` option.

### 3. Rejecting before the upgrade is free

The obvious worry — a failed auth must return an HTTP error *before* `upgrader.Upgrade` runs, the
way the existing unknown-ride 404 does — needs no special handling. `auth.Require` runs before
`ServeWS` is ever called and does not invoke `next`, so the upgrade never happens. Stated explicitly
so nobody adds machinery for it.

### 4. The real WebSocket problem is on the client

`wsClient.ts` already documents at length, for the 404 case, that a rejected handshake surfaces to
React Native as a generic `error` + `close` with platform-specific text. An expired token would
therefore produce an **infinite backoff loop against a wall** — the client cannot tell "unauthorized"
from "network flaky," so it would retry forever with no path to recovery.

The fix reuses machinery that already exists. `checkRideExists` is already a plain HTTP `GET` against
`/ws`, already run on attempt 0 and once backoff saturates. It gains a third outcome: **401 →
refresh the session once and retry; a second 401 → terminal `rejected`.** One refresh, not a loop,
because a token that fails immediately after a refresh is not going to start working.

Verification happens only at upgrade. A four-hour ride on a one-hour token stays connected, which is
deliberate — re-verifying mid-stream would need a token-refresh frame, a strictly larger protocol
change, for no security gain on a socket that already proved identity. What it *does* require is
that `getAccessToken()` is called inside `open()` on every attempt rather than once at app start, so
every reconnect presents a live token. That is the single most important sequencing detail here.

### 5. Claims

| Claim | Treatment |
|---|---|
| `sub` | **Trusted.** Becomes the rider id and the hub's seat key. |
| `exp` | Required, 30 s leeway. |
| `aud` | Must equal `"authenticated"`. |
| `iss` | Must equal `SUPABASE_URL + "/auth/v1"` — free, and blocks a token minted by a different project. |
| `role` | Must equal `"authenticated"`. |
| `is_anonymous` | Read, **not gated on.** Anonymous riders are first-class (`ADR-016`). |
| `email`, `user_metadata` | **Never trusted** — `user_metadata` is user-writable via `updateUser`. |

**The `aud`/`role` pair is the security-critical part, not ceremony.** In a legacy HS256 Supabase
project the public `anon` API key — shipped inside every APK, and correctly so per `ADR-016` §5 — *is
itself a JWT signed with the same secret*, carrying `role: "anon"`, no `aud`, and a ~10-year expiry.
Without both checks, anyone holding the app's public key holds a valid credential for the Go server.
Signature verification alone would pass it.

`jwt.WithValidMethods([]string{"HS256"})` pins the algorithm. That is the alg-confusion defence
`CLAUDE.md` demands, and the reason it insists on `golang-jwt/jwt/v5` rather than a hand-rolled
verifier.

### 6. `?rider=` is removed; `sub` is the seat key

`hub.ServeWS` reads `auth.Subject(ctx)`. `genID()` and `validRiderID()` become dead code and are
deleted rather than left for later.

The reconnect-replacement behaviour `ADR-010` built is unchanged in substance — a rider reconnecting
still evicts their own stale connection and carries their last fix forward. Only the source of the
key changes, from client-asserted to server-verified, which is strictly stronger: a rider could
previously have claimed any `rider` value, including another rider's.

### 7. A blank secret stops the process

`ORS_API_KEY` uses "warn at boot, 503 at the endpoint," which is right for a feature. Auth does not:
a blank `SUPABASE_JWT_SECRET` makes `run()` return an error and exit. An unset auth secret must never
degrade into "everything is open."

**No `DEV_NO_AUTH` escape hatch**, deliberately, because that flag gets left on.

### 8. HS256 for now, with the fork recorded

Supabase now defaults new projects to **asymmetric (ES256/RS256) signing keys** and documents the
HS256 shared secret as available for backward compatibility and no longer recommended. `CLAUDE.md`
specifies HS256 and `ADR-008` pre-authorised `golang-jwt/jwt/v5` as "the second and last" Go
dependency.

HS256 wins for v1: it is what is written down, it is one env var, and it costs zero network calls on
the request path. The JWKS path would add a third dependency, a fetch, a cache and a key-rotation
story to a server whose stated value is being small — and adding it would itself reverse part of
`ADR-008`, i.e. need its own record.

**The practical consequence, which is the most likely thing to go wrong in this whole phase:** if the
Supabase project is created with asymmetric keys, every token fails verification and the fix is a
dashboard setting, not code. Decide before creating the project.

## Alternatives Considered

### Per-route auth instead of one wrapping middleware

More explicit at each call site, and it would make the `/healthz` exemption obvious rather than a
special case inside the middleware. **Rejected** because it fails open by default: a route added
later is unauthenticated until someone remembers, and the failure is silent.

### Token in the query string

Simpler on every client, and it sidesteps React Native's non-standard `WebSocket` headers option
entirely. **Rejected** — `ADR-008` forbids it explicitly, and the reasoning holds independently of
what `logging.go` currently logs: a URL is visible to proxies, CDN logs and any future middleware
that logs `RawQuery`, in a way a header is not.

### Re-verify the token periodically over the live socket

Genuinely stronger: a revoked session would be cut mid-ride rather than at the next reconnect.
**Rejected** as a bad trade — it needs a new client→server refresh frame and server-side expiry
tracking, i.e. a materially larger protocol change than this record already makes, to close a window
that only matters if a session is revoked *during* a ride. Revisit if account compromise becomes a
real threat model rather than a hypothetical one.

### Keep `?rider=` alongside the JWT

It would preserve `wsClient.ts` and `hub.ServeWS` unchanged, and make this record a pure addition
with no protocol break. **Rejected:** two identifiers for one rider is two sources of truth, and the
client-asserted one is forgeable. If they ever disagreed, the code would have to pick — and the only
correct answer is the verified one, which means the other should not exist.

### Verify on the HTTP routes but not on `/ws`

The WS upgrade is the awkward one; the HTTP routes are trivial to protect. **Rejected** because
`/ws` is the endpoint that actually matters: it streams live location data for every rider in a
room. Protecting the route proxy while leaving the position stream open would be precisely backwards.

## Consequences

**Positive**

- Three documents stop describing a control that does not exist.
- The rider id becomes server-verified rather than client-asserted — a rider can no longer claim
  another rider's seat.
- `POST /geocode` and `POST /rides/{code}/route` stop being open ORS proxies, which retires a
  negative recorded in both `ADR-012` and `ADR-013` and removes the automatic-traffic exposure
  `ADR-014` flagged.
- `golang-jwt/jwt/v5` is the only new dependency, exactly as `ADR-008` pre-authorised.

**Negative**

- **Supabase is now on the critical path for every request**, not just for durable state. `ADR-016`
  records the same exposure for sign-in; this widens it to the whole API surface.
- **One account is one seat.** Two devices sharing a `sub` now evict each other. Correct for a
  motorcycle, and mostly invisible in practice since each install gets its own anonymous user — but
  a real trap when testing with two emulators from one session.
- **`sub` is visible to every co-rider** in the `state` frame. Knowing a uid grants nothing without a
  signed token, and today's per-install UUID is equally stable, so exposure is unchanged in kind. The
  one new property is cross-*ride* correlation among people who chose to ride together, which is not
  a threat. If it ever is, broadcasting `hex(sha256(sub || rideCode))[:16]` while keeping `sub` as
  the server-side key is roughly four lines.
- **`ADR-008` called `golang-jwt` the last Go dependency.** If the HS256 fork loses, JWKS adds a
  third and reverses that — which is its own ADR, and worth knowing before it is a surprise.
- Every existing backend test that opens a socket now needs a token.

## Trade-offs

| We gave up | We got |
|---|---|
| A Go server that runs standalone with no external identity provider | An identity Postgres RLS can actually enforce, and endpoints that are no longer open proxies |
| Mid-ride revocation | A protocol change limited to "add a header, drop a query param" |
| A forgiving `DEV_NO_AUTH` for local work | An auth boundary that cannot be accidentally left open |
| Client-chosen rider ids (and the flexibility of testing two riders from one session) | A seat key that cannot be spoofed |

## Future Revisions

Revisit if:

- **The Supabase project turns out to use asymmetric keys**, per Decision §8 — the migration to
  `MicahParks/keyfunc` and JWKS is the answer, and it reverses `ADR-008`'s dependency-count claim.
- **Session revocation during a ride becomes a real threat**, which is when the rejected periodic
  re-verification is worth its protocol cost.
- **Cross-ride `sub` correlation matters**, per the per-room hashing note above.
- **Rate limiting lands.** `main.go`'s middleware comment reserves a slot inside CORS; auth now
  occupies adjacent ground and the two should be considered together, since auth already rejects the
  cheapest class of abuse.

**What would *not* justify revisiting:** wanting a development bypass because tokens are inconvenient
in local testing. Decision §7 exists because that flag never gets turned back off; the answer is a
test helper that mints a valid token, which the test suite needs anyway.
