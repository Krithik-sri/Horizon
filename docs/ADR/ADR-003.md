# ADR-003: OpenFreeMap for tiles, not Google Maps or Mapbox

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-07-28 *(records a decision made during initial design; see `docs/SYSTEM_DESIGN.md` §4, §5.4)* |
| **Deciders** | Horizon team |
| **Supersedes** | — |

## Context

Horizon needs a map — it is the primary UI. Riders look at it for hours, on a handlebar mount, in
sunlight, on mobile data.

That breaks into **three separate concerns** that the commercial SDKs bundle together and that we
must be able to buy separately:

1. **Tiles** — the basemap imagery/vector data itself.
2. **Renderer** — the client library that draws tiles, a route line, and rider markers.
3. **Directions** — turning waypoints into a cycling route polyline.

Requirements:

- **Free with no credit card**, permanently ([ADR-006](./ADR-006.md)). This is a hard constraint.
- **The same renderer must work on web and native** — MapLibre GL JS in the browser today, MapLibre
  React Native later ([ADR-004](./ADR-004.md)) — with the same style URL and the same coordinate
  conventions (P7 ("every feature works for both web and mobile")).
- **A route line and per-rider markers**, both updated continuously. Markers move at 4 Hz.
- **Cycling-appropriate routing** — bike routing is genuinely different from driving routing.
- The tile source will be hit by ~15 riders for a few hours a week. Trivial volume.

The critical constraint, and the one that decides this: **every mainstream commercial map SDK
requires a credit card on file, even for a $0 free tier.** Google Maps Platform requires billing
enabled before it will serve a single tile. Mapbox requires a card for an account that can exceed
free limits, and its free tier is metered per map load.

## Decision

**We use three independent open pieces, none of which needs an account:**

| Concern | Choice | Auth |
|---|---|---|
| **Tiles** | [OpenFreeMap](https://openfreemap.org) — `https://tiles.openfreemap.org/styles/liberty` | **none** — no key, no signup, no card, no stated usage limits |
| **Renderer** | MapLibre — `maplibre-gl` (web) / `@maplibre/maplibre-react-native` (native) | n/a, it's a library |
| **Directions** | [OpenRouteService](https://openrouteservice.org) (cycling profile) | free API key, email signup, no card |

**The tile URL is a plain string in client code** (`web/src/map/Map.tsx:9`). There is nothing to
configure, nothing to rotate, and nothing to leak.

**ORS is called only from the Go backend**, so `ORS_API_KEY` stays server-side
(P8 ("secrets never leave the server")) and the shared daily quota is
controlled centrally — **one route fetch per ride, not per rider** (`CLAUDE.md`).

This decision is reinforced by a standing rule in `CLAUDE.md`: *"Don't add Mapbox, Google Maps, or
anything that requires billing."*

## Alternatives Considered

### Google Maps Platform

The most familiar maps to every user alive, excellent data quality, superb bicycle routing, Street
View, Places, and traffic. If money were available this would be a serious contender purely on
cycling-route quality.

**Disqualified immediately:** billing must be enabled with a valid credit card before the API serves
anything, even within the free monthly credit. There is no card-free path. It also violates the
separation we need — Google's SDK bundles tiles, renderer, and routing behind one billed key, so we
couldn't swap one piece. And `react-native-maps` with the Google provider needs the same billing.

### Mapbox

The best developer experience in the category. `mapbox-gl-js` is superb, the styling tools are
excellent, `rnmapbox` is mature, and Mapbox Directions has a real cycling profile. **MapLibre is
literally a fork of Mapbox GL JS v1**, so we get most of the API surface anyway.

**Rejected:** an account with a credit card is required for anything beyond a small metered free
tier, and the tier is per map load — a metric that grows with exactly the usage pattern we have
(riders reloading the app). More subtly, Mapbox relicensed GL JS to a proprietary license at v2,
which is *why* MapLibre exists. Choosing Mapbox would mean depending on a vendor that has already
demonstrated it will change licensing terms on a library people depend on.

### MapTiler

**The strongest runner-up, and worth stating clearly: MapTiler needs no credit card.** Free tier,
email signup only, high-quality vector tiles, and it works with MapLibre — the renderer choice is
unaffected. `docs/SYSTEM_DESIGN.md` §4 records it as the considered alternative.

**Why OpenFreeMap won anyway:** MapTiler requires *an account and an API key*; OpenFreeMap requires
*nothing at all*. That difference sounds cosmetic and isn't:

- A key is a secret-shaped thing in client code. It gets committed, leaked, rate-limited, or
  rotated. A public style URL cannot be any of those.
- A key means an account, which means an owner, which means a bus factor and a renewal to forget.
- MapTiler's free tier is metered (map loads/month); OpenFreeMap publishes no such limit.
- Onboarding a contributor drops from "sign up, get a key, put it in `.env.local`" to "clone and
  run". That is a real velocity gain, permanently.

**MapTiler remains our first fallback** if OpenFreeMap degrades — see Future Revisions.

### Stadia Maps

Same shape as MapTiler: MapLibre-compatible, free tier, account required, metered. Loses for the
same reason.

### Self-hosted tiles (OpenMapTiles / Protomaps / tileserver-gl)

Complete control, no external dependency, no rate limits, and Protomaps' single-file PMTiles format
is genuinely elegant. This is the *endgame* if usage ever grows.

**Rejected for v1:** planet-scale vector tiles are tens of gigabytes; regional extracts are still
gigabytes. That means storage, bandwidth, and a tile server — all of which cost money, which
[ADR-006](./ADR-006.md) forbids. It also adds an operational burden to a project whose entire backend
is one 340-line binary. Renting the hard part is the point (`docs/SYSTEM_DESIGN.md` §"Design principles":
*don't build what you can rent*).

### Raster OpenStreetMap tiles (`tile.openstreetmap.org`)

Free and no key. **Rejected:** the OSMF tile usage policy explicitly prohibits use by apps at any
meaningful scale, raster tiles can't be restyled or rotated, they look poor on high-DPI phone
screens, and vector tiles are strictly better for a map with a moving route line and markers.

### Directions: alternatives to ORS

- **Self-hosted OSRM or Valhalla** — no signup at all, and Valhalla's cycling costing is excellent.
  Rejected for the same reason as self-hosted tiles: it's a server to run and pay for. **This is the
  documented escape hatch** if ORS quota becomes binding.
- **GraphHopper** — good cycling routing, free tier, but requires an account and has a low daily cap.
- **Mapbox/Google Directions** — card required.

ORS won on: free key with email only, real cycling profiles (including `cycling-road`,
`cycling-mountain`, `cycling-safe`), an open-source implementation we could self-host later, and a
daily cap that our once-per-ride fetch rule keeps us far below.

**Note that OpenFreeMap deliberately serves *only* tiles** — no routing, no search, no geocoding.
That's exactly why directions are a separate decision going to a separate provider. The unbundling
is a feature, not an inconvenience.

## Consequences

**Positive**

- **Zero cost, zero accounts, zero cards for the map.** A new contributor clones the repo and the map
  works. No key to provision, no `.env` entry, no onboarding step.
- **No secret in the client.** The tile URL is a public string. Nothing to leak, nothing to rotate,
  nothing to rate-limit per-key.
- **One renderer, two platforms.** MapLibre GL JS and MapLibre React Native consume the *same style
  URL* and share coordinate conventions and layer concepts. The Phase-2 route line is a
  `ShapeSource` + `LineLayer` on both. This is P7 ("every feature works for both web and mobile")
  working as intended.
- **The three concerns are independently replaceable.** Swapping tiles is a one-line style URL
  change. Swapping directions is a change in one backend package. Swapping the renderer is the only
  expensive one — and MapLibre is BSD-licensed with an active foundation behind it.
- Attribution is added automatically by MapLibre, so OSM's license terms are satisfied by default.
- The ORS key never reaches a client, and the once-per-ride fetch keeps us at a handful of requests
  per week against a daily cap in the thousands.
- MapLibre's imperative model is cleanly quarantined in `web/src/map/`, which is also the single site
  of the `[lng, lat]` conversion.

**Negative**

- **OpenFreeMap and ORS are donation-funded community services.** No SLA, no support contract, no
  uptime guarantee. If OpenFreeMap goes down mid-ride, the map goes blank. We have no fallback style
  URL configured and no cached tiles (HZ-29) — offline, the app loads and shows nothing.
- **No CDN in front of tiles.** Every rider pulls directly from OpenFreeMap. Polite usage matters;
  runtime tile caching (HZ-29) would be both useful to us and considerate to them.
- **Map data quality varies by region.** OSM cycling infrastructure coverage is excellent in Western
  Europe and patchy elsewhere. Google would be better in some geographies.
- **No bundled search or geocoding.** Turning "the café on Main Street" into coordinates needs
  another service (Nominatim, also donation-funded). This is why the Phase-2 destination picker is
  deliberately crude — pasted coordinates first (HZ-14).
- **ORS has a hard daily cap per key**, and nothing in the code currently *enforces* the
  once-per-ride rule — it's a convention. HZ-10 must implement it.
- **The coordinate-order trap.** MapLibre and GeoJSON use `[lng, lat]`; our protocol uses named
  `lat`/`lng` fields. `CLAUDE.md` calls this "a known trap" and the discipline of converting at
  exactly one site is a rule we now have to enforce forever.
- No turn-by-turn navigation. Route line plus your own position is the scope
  (`docs/SYSTEM_DESIGN.md` §1 non-goals).

## Trade-offs

| We gave up | We got |
|---|---|
| Google's cycling data quality and global consistency | Zero cost and zero accounts, permanently |
| A commercial SLA and support | No secret in the client, nothing to rotate or leak |
| Bundled search, geocoding, and turn-by-turn | Three independently replaceable pieces |
| Mapbox's developer experience and styling tools | A BSD-licensed renderer that can't be relicensed out from under us |
| Guaranteed uptime | A one-line style URL as the entire map configuration |

**We are deliberately depending on donation-funded infrastructure for a hobby app.** That is an
appropriate match — our load is a rounding error on their traffic, and the failure mode (a blank
basemap; dots, route line, and standings all still work) is degraded, not broken. It would be an
inappropriate match for a product with paying users.

## Future Revisions

Revisit if:

- **OpenFreeMap becomes unreliable or shuts down.** Migration is a **one-line style URL change** to
  MapTiler or Stadia — both MapLibre-compatible, both card-free. The cost is adding an account and a
  key to onboarding. **Keep a MapTiler style URL noted as the standby.** This is the cheapest
  reversal in the entire architecture and it is worth preserving that property: never let anything
  other than the style URL depend on the tile provider.
- **ORS quota becomes binding.** First enforce once-per-ride caching properly, then cache route
  responses server-side keyed by waypoints, then self-host Valhalla or OSRM. Provider change is
  isolated to one backend package by design.
- **Cycling data quality proves inadequate in the riding area.** Contribute to OSM — genuinely the
  right answer for a local friend group and cheaper than switching providers. Only then evaluate a
  paid provider, which requires revisiting [ADR-006](./ADR-006.md) first.
- **Usage grows past community-service etiquette.** Self-host tiles (Protomaps/PMTiles is the
  lowest-effort path) and ORS. Both are open source, and `docs/SYSTEM_DESIGN.md` §9 lists this as step 4
  of the scaling path.
- **Offline maps become a requirement.** Currently an explicit non-goal. It would mean bundling
  regional PMTiles — a large change, and a reason to revisit this ADR properly rather than patch it.

**What would *not* justify revisiting:** wanting a nicer default style (restyle MapLibre — it's free),
wanting search (add Nominatim separately — the unbundling makes that easy), or a contributor's
familiarity with the Mapbox SDK.
