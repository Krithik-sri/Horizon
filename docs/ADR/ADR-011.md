# ADR-011: Navigation is a first-class Horizon capability

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-02 |
| **Deciders** | Horizon team |
| **Supersedes** | — |
| **Amends** | [ADR-003](./ADR-003.md) (Consequences: the turn-by-turn non-goal) and [ADR-006](./ADR-006.md) (Consequences: the card-required claim) — not superseded, see "Correcting ADR-003 and ADR-006" below |

## Context

`docs/PRODUCT.md` said, in eleven places, that Horizon is "NOT another navigation app." That
denial was never fully true of the design system: `docs/DESIGN.md`'s **Ahead** zone — the top 34%
of every Motion-register layout — is defined as holding *"Next turn, upcoming hazard, distance
remaining."* A design system that reserves a third of the strictest register's screen for turn
cues was already built for turn-by-turn navigation while the product document forbade it. That's
not a stylistic inconsistency; it's two source-of-truth documents disagreeing about what the
product is.

The repo owner has resolved the disagreement: **Horizon does provide navigation** — a route line
plus turn-by-turn maneuver cues — alongside convoy and trip planning. It is the first MVP feature,
not a later addition.

The stated reason navigation was excluded was also wrong on the facts. `ADR-006`'s Consequences
section says: *"Turn-by-turn navigation, geocoding and search, guaranteed-uptime hosting, and
managed auth are all card-required or self-host-only. That's why turn-by-turn is an explicit
non-goal."* `ADR-003` repeats the conclusion: *"No turn-by-turn navigation. Route line plus your
own position is the scope."*

That's incorrect. OpenRouteService's `/v2/directions/{profile}/geojson` endpoint — the same free,
no-card, email-signup-only endpoint `ADR-003` already chose for the route line
(`driving-car` profile) — returns `properties.segments[].steps[]` with turn-by-turn instructions
**on the same response that returns the route geometry**. There is no second request, no
additional account, and no additional cost. The non-goal was never a card problem. It was an
oversight: nobody read past `geometry` in the ORS response shape when `ADR-003` was written.

## Decision

### Navigation is named, not excluded

Route line plus turn-by-turn maneuver cues is a named Horizon capability, alongside convoy and
ride planning — not a reduced version of what a "real" navigation app does, and not a later phase.
`docs/DESIGN.md`'s Ahead zone already assumed this; the product document now agrees with its own
design system.

**Explicitly still out of scope**, and not decided by this ADR: off-route rerouting, spoken audio
guidance, and destination search (geocoding). Navigation here means *route line + maneuver cues
computed once from a start and an end point the rider already chose* — nothing that requires a
standing relationship with the rider's live position beyond what convoy tracking already sends.

### Correcting ADR-003 and ADR-006

ADRs are append-only, so a wrong claim doesn't get edited — it gets corrected by a later ADR that
says so plainly. This record corrects two specific claims and touches nothing else in either
document:

- **`ADR-003`, Consequences:** *"No turn-by-turn navigation. Route line plus your own position is
  the scope (`docs/SYSTEM_DESIGN.md` §1 non-goals)."* — **Corrected.** ORS returns turn
  instructions on the same free call as the route geometry. The scope now includes maneuver cues.
- **`ADR-006`, Consequences:** *"Turn-by-turn navigation, geocoding and search, guaranteed-uptime
  hosting, and managed auth are all card-required or self-host-only. That's why turn-by-turn is an
  explicit non-goal."* — **Corrected, and the premise was factually incorrect.** Turn-by-turn does
  not require a card. Geocoding/search, guaranteed uptime, and managed auth remain accurate
  examples of card-required or self-host-only capabilities; only turn-by-turn was misclassified.

**Neither ADR is superseded.** `ADR-003`'s tile/renderer/directions choices — OpenFreeMap,
MapLibre, ORS `driving-car` — stand entirely unchanged; this record only corrects what ORS's free
tier was believed to exclude. `ADR-006`'s no-card rule stands and remains upstream of this
decision too: navigation is affordable *because* it fits inside a constraint this ADR does not
touch, not because the constraint relaxed. The index in `docs/ADR/README.md` marks both records
**amended by 011**, not superseded — their Status stays `Accepted`.

### Protocol: a new `route` message

A route (geometry, turn steps, and a distance/duration summary) is pushed to clients as its own
server→client WebSocket message, not as a field on `state`:

```json
{ "type": "route", "ride": "ABC123",
  "polyline": [[77.5946, 12.9716], [77.5951, 12.9720]],
  "steps": [ { "instruction": "Turn right onto NH 44", "distance": 420.5,
               "duration": 31.2, "type": 1, "name": "NH 44", "wayPoints": [12, 47] } ],
  "summary": { "distance": 18240.3, "duration": 1620.7 } }
```

Sent once to a client on join if its room already has a stored route, and once to every client
currently in the room whenever a route is set (`POST /rides/{code}/route`) or replaced.

**Why its own message, not a field on `state`.** `state` goes out at a fixed ~4 Hz to every rider
in the room (`docs/ADR/ADR-002.md`). A route polyline can run to thousands of coordinate pairs.
Putting it on `state` would multiply the bandwidth of the highest-frequency message in the
protocol by orders of magnitude, for data that changes approximately never during a ride. `route`
carries exactly the data that's route-shaped and is sent exactly as often as a route changes.

**`polyline` is `[lng, lat]` — MapLibre/GeoJSON order — deliberately, and it is the one place in
the protocol where that's true.** Every other message (`loc`, `state`) uses named `lat`/`lng`
fields, precisely because `CLAUDE.md` calls the coordinate-order mismatch between our protocol and
MapLibre/GeoJSON "a known trap" and mandates converting at one explicit boundary. `route` *is*
that boundary: the array is built server-side already in map order, so a client drops it straight
into a `ShapeSource` with zero client-side transformation. `wayPoints` are indices into `polyline`
— a client compares its position along the line to a step's `wayPoints` to know which step is
next. `steps` and `summary` may be `null` (a route can exist with only a geometry, if ORS's
directions response ever omits them).

`loc`, `welcome`, and `state` are unchanged by this ADR.

### One *stored* route per ride, replaceable

`CLAUDE.md`, `ADR-003` (Decision, lines 50–52), and `ADR-006` (§Standing rules, item 4) all state
the same rule: fetch a route **once per ride, not once per rider**. That per-rider prohibition is
unchanged — it is still exactly one ORS call for the group, never one per rider, regardless of how
many times a route changes.

What relaxes is the word "once": it becomes **once per stored route, and the stored route is
replaceable.** A rider changing destination mid-ride has to be able to set a new one — a rule that
forbade any second fetch for the whole ride would forbid that outright, which was never the
intent. `POST /rides/{code}/route` now replaces the room's stored route rather than being
meaningful only the first time it's called, and every client in the room gets the new `route`
message.

This is a low-stakes relaxation to record, not a quota risk. ORS's free tier is 2,000
requests/day and 40/minute; a handful of route changes across a ride — a wrong turn, a rider
suggesting a detour — is nowhere near either ceiling. It gets recorded anyway because "once per
ride" was a documented rule in three places, and a documented rule changing needs a documented
reason, not a silent drift.

## Alternatives Considered

### Ship the route polyline on `state`

The simplest possible protocol change — one field, no new message type, nothing for a client to
listen for beyond what it already parses.

**Rejected:** `state` is the one message in the protocol explicitly designed to be small and
constant-cost regardless of what's happening in the ride (`docs/ADR/ADR-002.md`). A route can be
thousands of points; sending it 4 times a second to every rider, unconditionally, for data that is
static for the length of the ride, is exactly the kind of amplification ADR-002 built the fixed
tick to avoid.

### Full turn-by-turn now: rerouting, spoken guidance, destination search

Genuinely tempting, since turn instructions are already sitting in the ORS response this ADR
starts using — spoken guidance and rerouting are the features people mean when they say "turn-by-
turn navigation."

**Rejected for this ADR, not forever.** Each is a separate, larger decision this record doesn't
make: rerouting means detecting divergence from the stored polyline and re-calling ORS
automatically (a new client/server behavior, and its own quota question); spoken guidance means
picking a point on the Attention Ladder for maneuver cues, which is a `horizon-design` call, not
an architecture one; destination search means geocoding, which `ADR-003`'s Consequences already
flags as unbundled from ORS and unsolved. Bundling all of it into "navigation" here would smuggle
three undecided features in under one ADR, which rule 3 in `docs/ADR/README.md` — one decision per
record — exists to prevent.

### Keep "once per ride" strictly immutable; require a new ride code to change destination

The narrowest possible reading of the existing rule: don't relax it, work around it. A destination
change starts a fresh ride.

**Rejected:** it solves the letter of the rule at the cost of the product. Ending and re-joining a
convoy's live session just to change where the ride is going would scatter riders across two rooms
mid-ride — the exact ghost-convoy problem `ADR-010` closed for reconnects, self-inflicted this
time by protocol design instead of a network drop.

### Cache routes server-side keyed by waypoints, independent of "once per ride"

`ADR-003`'s Future Revisions already names this as the next lever if ORS quota becomes binding:
cache by `(start, end)` so identical requests across rides don't re-hit ORS at all.

**Not adopted here, and not rejected either — out of scope.** It's an optimization for quota
pressure that doesn't currently exist (see the 2,000/day math above). It remains the documented
next step in `ADR-003` if usage ever grows into it; this ADR doesn't need it to make route changes
replaceable.

## Consequences

**Positive**

- The product document and the design system agree with each other for the first time on this
  point — `docs/DESIGN.md`'s Ahead zone was always designed for this.
- A rider can change destination mid-ride without ending the convoy session, closing a real gap
  the old "once per ride" wording left unaddressed.
- Turn instructions cost nothing extra to obtain — they were already in the ORS response
  `ADR-003` chose; this is a client/protocol change, not a new backend dependency.
- The `route` message's shape (positional `[lng, lat]`, `wayPoints` as indices) needs no
  server-side reshaping of ORS's own response beyond what the route proxy already does.

**Negative**

- **A garbage-collected room loses its stored route.** `ADR-010` sweeps a room 5 minutes after it
  empties; `ADR-002`'s Negative consequences already flag that routes don't survive a restart
  because no client re-POSTs one. That gap is unchanged by this ADR and now matters more, since a
  route is a first-class capability instead of a nice-to-have line on the map.
- **Turn-by-turn raises the stakes on "never interrupt a corner."** A maneuver cue is inherently
  time-sensitive — a "turn right in 50m" delivered late is wrong, not just late — which is a
  harder constraint to sit inside the Attention Ladder than an ambient route line was. This ADR
  adds the data channel only; how maneuver cues are surfaced without violating the corner rule is
  a `horizon-design` decision this record deliberately leaves open.
- **The Go server now holds a route in memory per room**, where previously it held only rider
  positions. This does not touch Postgres and does not violate `CLAUDE.md`'s "no database in the
  Go server" rule — it's ephemeral, room-scoped state exactly like rider positions — but it is one
  more piece of state `Room` owns, alongside the rider map `ADR-010` already guards under
  `Hub.mu`.
- **Scope creep risk.** Turn-by-turn instructions sitting in memory is an obvious invitation to
  add rerouting or spoken guidance next. Both are explicitly out of scope for this decision (see
  Alternatives Considered) and need their own ADRs if and when they're actually built.

## Trade-offs

| We gave up | We got |
|---|---|
| A strictly immutable "one fetch, ever, per ride" rule | A rider can change destination mid-ride without restarting the convoy |
| Simplicity of one WebSocket message shape (`state` only) | A `route` message sized for what it carries, that doesn't tax the 4 Hz tick |
| The comfort of a wire format that's positional nowhere else | A `polyline` a client can hand straight to MapLibre with zero conversion |
| Treating turn-by-turn as permanently out of reach | A capability that cost nothing extra once the ORS response was actually read |

## Future Revisions

Revisit if:

- **Riders diverge from the stored route often enough that off-route rerouting is worth its own
  decision.** This ADR deliberately doesn't build it — see Alternatives Considered.
- **The corner-safe delivery of maneuver cues turns out to need a protocol change**, not just a
  design decision — e.g. a cue needing to carry urgency or distance-to-turn beyond what `steps[]`
  already has. Currently `steps[].distance`/`wayPoints` look sufficient; revisit only if a client
  implementation proves otherwise.
- **ORS quota pressure becomes real** at the route-change rate this ADR now permits. Then
  `ADR-003`'s Future Revisions path applies as written: cache by waypoints, then self-host.
- **Room GC losing an unsaved route becomes a recurring complaint**, not just a documented gap.
  The fix is a client re-POST on reconnect, or persisting the last route through a room's grace
  period — either is a small change once it's actually needed.

**What would *not* justify revisiting:** wanting spoken guidance or destination search sooner —
both are known, deliberate exclusions from this decision, not oversights.
