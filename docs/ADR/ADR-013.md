# ADR-013: A route can be fetched without being stored or broadcast, and alternatives are a pre-commit concern

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-10 |
| **Deciders** | Horizon team |
| **Supersedes** | — |
| **Amends** | [ADR-011](./ADR-011.md) (Decision → "one *stored* route per ride, replaceable": that rule stands for every route the convoy sees, but this record carves out a class of route fetch that deliberately never reaches the store or the wire) — not superseded, the `route` message protocol is untouched |

## Context

`ADR-011` settled where a route lives:

> "one *stored* route per ride, replaceable — still never one fetch per rider" (`ADR-011`, Decision)

That rule was written for a flow with exactly one shape: pick a destination, get a route, everyone
sees it. `mobile/src/features/departure/DestinationSearch.tsx` implements precisely that — tapping a
search result calls `setDestination`, which POSTs two waypoints and broadcasts the result to the
whole room. There is no intermediate state, because there was never anything to decide.

A multi-stop planner breaks that assumption. A rider building a route adds a stop, sees what it does
to the line, drags it later in the order, adds another, removes the first. Every one of those edits
wants a route drawn on a map. **None of them is a decision.** Under today's flow each would fan out
to every rider in the convoy, so a co-rider waiting at a petrol stop would watch the group's route
flicker through six half-built shapes before settling.

The same gap appears from the other direction with alternative routes. ORS's
`/v2/directions/{profile}/geojson` accepts `alternative_routes` and returns up to three routes on one
response — the same shape `ADR-011` already noted for `steps`: no second request, no extra cost. But
three routes are only interesting *before* a choice is made. Once the rider picks one, the convoy
needs exactly one route, which is what `ADR-011` already specified and what
`backend/internal/hub/room.go`'s single `routeMsg []byte` already stores.

Both problems are the same problem: **there is currently no way to ask the backend for a route
without telling everyone about it.**

## Decision

### 1. `preview: true` on the existing endpoint — one mechanism, not two

`POST /rides/{code}/route` gains three optional fields:

```go
type routeRequest struct {
	Waypoints    [][2]float64 `json:"waypoints"`
	Preview      bool         `json:"preview"`      // return to this caller only; no store, no broadcast
	Alternatives bool         `json:"alternatives"` // ask ORS for up to 3 (two waypoints only)
	Index        int          `json:"index"`        // which route to commit; ignored when Preview
}
```

When `Preview` is true the handler runs identical validation and the identical ORS call, then returns
the result and skips `hub.SetRoute` entirely. Nothing is stored, nothing is broadcast, no rider other
than the caller learns the request happened.

**This is deliberately a flag on the ride-scoped endpoint, and not a new un-scoped `POST /route`.**
The un-scoped variant was the first design, and it has a real argument behind it: a flag whose
default is "broadcast to the convoy" is exactly the flag someone forgets to set. It was rejected on
two counts that outweigh that. First, `backend/geocode.go` is already an unauthenticated ORS proxy
and `ADR-012` recorded the resulting shared-quota exposure as a negative; a second one doubles the
surface that can burn the account, and the ride-scoped path's existing 404-on-unknown-code check is
the only thing currently gating any of it. Second, Go's zero value for a `bool` is `false`, so the
forgotten-flag failure mode runs in the safe direction — an omitted `preview` broadcasts, which is
today's behaviour and today's only caller's intent.

The same mechanism serves any future need for a route that belongs to one screen rather than to the
room. That is stated here so the next such feature reaches for this flag instead of adding a third
endpoint.

### 2. Alternatives are pre-commit only — the room still stores exactly one route

`hub.SetRoute`, `Room.routeMsg`, and the server→client `route` message are **unchanged**. No rider
ever receives three polylines. The Motion register never sees an alternative.

The flow: the planner asks for a preview with `alternatives: true` and gets up to three routes back
over HTTP. It holds all three client-side and renders them as a choice. On commit it POSTs the same
waypoints with `preview` unset and `index` set, and the handler broadcasts `routes[index]`.

The alternative design — store all three on the room, add a `SelectRoute` endpoint, and re-broadcast
an already-stored frame on selection — was worked out in full before being dropped. It is genuinely
cheaper in ORS requests (selection costs nothing, where the design above costs one commit call on top
of the preview calls). It was rejected because it reshapes `Room.routeMsg` into `routeMsgs [][]byte`
plus a selection index, changes what a late joiner receives, adds a hub method and its concurrency
story, and triples per-room polyline memory — all to support re-picking a route *after* the convoy has
been told about it, which is a feature nobody asked for. `ADR-010`'s single-lock hub is worth more
than one ORS request per committed ride.

### 3. Alternatives are requested only when they will work

ORS caps `target_count` at 3 and refuses alternatives entirely above roughly 100 km of route — a
limit a motorcycle day ride clears routinely, and one that turns a working request into a 400 rather
than degrading. Two guards, both required, neither sufficient alone:

- **Ask only when the two waypoints are under 60 km apart** by haversine. Road distance runs about
  1.2–1.4× straight-line, so 60 km straight sits under the road-distance cap with margin.
- **Retry once without alternatives** on a non-`ErrNoRoute` 4xx. The gate makes this rare; the retry
  is what stops a coastal detour under 60 km straight-line from failing outright.

Alternatives are requested only when `len(waypoints) == 2`. Whether ORS accepts via-points together
with alternatives is not documented either way, and both call sites that want alternatives send
exactly two.

Tuning is `weight_factor: 1.4, share_factor: 0.6`, against ORS's own example values of 2 and 0.8.
Those defaults permit a route up to twice the optimal weight sharing 80% of its geometry, which in
practice yields two near-duplicates and one absurd detour. For a convoy the useful alternative is a
genuinely different road that isn't much slower.

### 4. The planner is its own screen with its own map component

The planner lives at `mobile/src/app/plan/[code].tsx`, not inline in `mobile/src/app/index.tsx`. The
Departure screen is a `ScrollView`, and a full-bleed MapLibre canvas inside a scroll container is a
gesture conflict with no clean resolution.

It gets a new `mobile/src/features/departure/PlannerMap.tsx` rather than a generalized
`MapCanvas.tsx`. This runs against the repo's standing reuse-first bias, so the reasoning is
recorded: roughly 70 of `MapCanvas.tsx`'s 96 lines *are* the Motion camera — `nextBearing` smoothing,
`CAMERA_PITCH = 45`, a `CAMERA_DURATION` that exists specifically to satisfy the Motion register's
120 ms animation cap, and a `topPadding` derived from the `horizon.ahead` token. A planner needs none
of it and wants the opposite of most of it. Generalizing would put a register branch inside the one
component whose camera behaviour is safety-relevant, which is how a wrong prop passed from Departure
becomes a Motion regression. What is actually shared is the style URL, which becomes an export.

`RouteLine` and `DestinationMarker` are reused unchanged — `RouteLine` with `progress={null}` already
draws one full `amber.core` line, which is exactly the right preview treatment.

### 5. No search-as-you-type

`DestinationSearch.tsx` stays submit-only. Autocomplete at any usable debounce turns one destination
into three to five geocode calls, and the planner's own preview requests draw on the same 40/minute
bucket — so a rider's typing would rate-limit the thing they are typing toward. The debounce budget
is spent on route previews instead, where it buys a redrawn line rather than a dropdown. If this
needs revisiting, the first lever is a cache keyed on the normalised query string, not a longer
debounce.

## Alternatives Considered

### Broadcast every planner edit live

Zero backend change — the planner would simply call the existing `setDestination` on each edit and
let the convoy watch the route evolve. There is a real argument for it beyond laziness: a co-rider
would see the plan taking shape and could object before it was committed, which is closer to how a
group actually decides where to go. **Rejected** because it inverts `docs/PRODUCT.md`'s Confidence
pillar — *"if information cannot be trusted, it should not be shown."* A route line that is going to
change six more times in the next minute is precisely information that cannot be trusted, and the
rider seeing it has no way to know which state is real. Group agreement is a conversation, which is
what `ADR-005`'s voice channel is for.

### A separate un-scoped `POST /route` for non-broadcast fetches

Covered in Decision §1. Its genuine upside — no flag to forget, and the safe behaviour is the only
behaviour — was weighed against doubling the unauthenticated ORS proxy surface `ADR-012` already
flagged as a negative. The bool's zero value resolving to today's behaviour is what tipped it.

### Store alternatives on the room with a `SelectRoute` endpoint

Covered in Decision §2. Cheaper in ORS quota, and it would let any rider re-pick after commit.
Rejected against the hub reshape and the memory cost it requires.

### Generalize `MapCanvas` with a register prop instead of a second component

Covered in Decision §4. Fewer files, one map component to maintain, and the repo's own bias points
this way. Rejected because the shared surface is one string constant and the unshared surface is the
camera behaviour that keeps a rider's eyes on the road.

### Reverse-geocode map-tapped stops so every stop has a real name

A stop reading "Point on map" in the list is genuinely worse than one reading "Nandi Hills".
**Rejected** on quota: it spends a geocode request per tap on a label, in the same 40/minute bucket
the previews need, for information the rider already has — they just tapped the place they meant.

## Consequences

**Positive**

- A rider can build and see a multi-stop route without the convoy watching them think.
- Alternatives cost no protocol change, no hub change, and no extra ORS request beyond the preview
  that was happening anyway.
- The `route` message, `hub.SetRoute` and `Room.routeMsg` are untouched, so `ADR-011`'s protocol and
  `ADR-010`'s single-lock hub both stand exactly as written.
- The preview mechanism generalizes: any future need for a route that belongs to one screen rather
  than to the room is already served.

**Negative**

- **Previews become the dominant consumer of the ORS quota.** Each settled edit is one request, so a
  six-stop planning session costs roughly seven where today's flow costs one — and a committed route
  now costs the previews plus one. The binding limit is 40/minute, not 2,000/day; the 600 ms debounce
  is the only thing keeping a fast reorderer under it. `ADR-012` already recorded geocode and routing
  sharing this ceiling; this record adds a third and larger claimant.
- **`preview` is a flag that must be correct.** Decision §1 argues the failure mode runs safe, but
  "the zero value is the safe one" is a weaker guarantee than "the unsafe thing does not exist."
- **A map tap can add a phantom stop.** MapLibre's `onPress` fires on a light tap during pan
  exploration. Removal is one tap, which is the mitigation; if it proves worse than that on real
  hardware the fix is gesture discrimination, not a mode toggle.
- **Alternatives are silently unavailable on long routes**, which is most of the interesting ones. A
  rider planning a 200 km day gets one route with no indication that alternatives were even possible.
- **A backgrounded planner can outlive its room.** The 5-minute empty-room GC does not fire while the
  socket is open, but a dropped socket plus five minutes gives a 404 on commit. That path needs a real
  message, not a silent failure.

## Trade-offs

| We gave up | We got |
|---|---|
| One meaning for "POST a route" — it now does two things depending on a flag | A planner that doesn't broadcast half-built routes, with no second endpoint and no protocol change |
| Free route re-selection after commit, and one ORS request per committed ride | `Room.routeMsg`, `hub.SetRoute` and the `route` frame unchanged |
| One map component | A Motion camera with no register branch in it |
| Search-as-you-type, which every rider expects | A quota that previews can actually use |
| Real names on map-tapped stops | Roughly one geocode request per planning session instead of one per tap |

## Future Revisions

Revisit if:

- **ORS quota pressure becomes real.** This record makes it materially more likely than `ADR-012`
  estimated. `ADR-003`'s path applies — cache first, keyed on the normalised waypoint list, then
  self-host.
- **Riders report picking a route blind**, because the alternatives list is text-only in the panel
  while the map draws only the selected route. Drawing all three at once in `amber.dim` with the
  selected one in `amber.core` is the obvious next step and needs no new decision.
- **The 60 km alternatives gate proves badly calibrated** against real ORS behaviour. It is a guess
  from a documented road-distance cap, not a measurement.
- **A third feature wants a non-broadcast route fetch.** If the `preview` flag starts carrying
  unrelated meanings, that is the signal to split it — not before.

**What would *not* justify revisiting:** wanting the convoy to see the plan as it is built. That is
the decision, not an omission — Decision §1 and the first rejected alternative both exist to record
it.
