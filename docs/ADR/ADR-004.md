# ADR-004: PWA first, native app later

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-07-28 *(records a decision made during initial design; see `docs/SYSTEM_DESIGN.md` §1 "Client decision")* |
| **Deciders** | Horizon team |
| **Supersedes** | — |

## Context

The original design targeted React Native + Expo — `docs/SYSTEM_DESIGN.md` §3 and §5.1 both describe a
native app, and `mobile/` was scaffolded with MapLibre RN, LiveKit RN, and WebRTC installed and the
iOS/Android permission config written. Then the client decision was reconsidered before the app code
was written, and reversed.

What forced the reconsideration:

**The actual usage pattern.** Riders mount the phone on the handlebars, screen on, for the duration
of the ride. That is not a guess — it is how you use a live map while cycling. Nobody rides staring
at a pocketed phone.

**What that implies:** if the screen is on and the app is in the foreground, a browser can do
everything a native app can for this workload. `navigator.geolocation.watchPosition` delivers
high-accuracy fixes, `navigator.wakeLock` keeps the screen from sleeping, MapLibre GL JS renders the
same OpenFreeMap style as MapLibre RN ([ADR-003](./ADR-003.md)), and the global `WebSocket` speaks
the same protocol ([ADR-002](./ADR-002.md)) to the same unchanged backend.

**The one thing a browser genuinely cannot do** is background location. When the tab is hidden or
the screen locks, browsers suspend `geolocation` — and **no service-worker trick changes this.**
`docs/SETUP_WEB.md:176` is explicit about it. That capability is real, and it is the sole justification
for `mobile/` existing at all.

**The cost of native, measured concretely:**

- MapLibre and LiveKit need native code, so it's a **custom Expo dev client, not Expo Go**. Every
  native dependency change means an EAS build.
- The dev host is Windows, so Android builds locally and **iOS requires EAS cloud builds**.
- Background location is an OS-permissions problem — iOS "Always", Android foreground service plus
  notification. `docs/SYSTEM_DESIGN.md` §10 names it *"the #1 pain"* and says to *"budget real time here."*
- Distribution means TestFlight or sideloading. Sharing a ride means "install this build first."

Against that, the PWA's cost is one URL and an "Add to Home Screen" tap.

## Decision

**The v1 client is an installable PWA (`web/` — Vite + React + TypeScript). The React Native app
(`mobile/`) remains the documented path for true background location, deferred to Milestone 4.**

The bet, stated plainly: **a screen wake lock covers the actual use case, so the one thing a browser
can't do never bites in v1.**

Consequences that are load-bearing:

- **The Go backend is client-agnostic and requires zero changes** for either client. `ServeWS` reads
  query params and speaks JSON; nothing is browser-specific.
- **`web/` is the reference implementation.** The mobile client ports from it, not the reverse.
  `types.ts` and the zustand store copy over unchanged; `ws.ts` needs only its identity backend
  swapped from `sessionStorage` to AsyncStorage.
- **`mobile/` keeps its native config.** The `UIBackgroundModes` and Android foreground-service setup
  in `app.config.ts` is precisely the payload that justifies the directory, and it is already
  written. Deferring the app does not mean discarding that work.

## Alternatives Considered

### React Native / Expo first — the original plan

Real background location, better battery control (`timeInterval`/`distanceInterval` push throttling
into the OS rather than dropping fixes in JS *after* the expensive part already happened), native map
performance, background audio for voice, and access to every device API without a permission
workaround. `mobile/` was already scaffolded with the hard permission config written, so a real head
start existed.

**Why it lost:** every one of those advantages except background location is a *refinement* of
something the browser already does adequately. Background location is the only capability gap — and
it does not matter when the phone is mounted with the screen on. Paying the dev-client build loop,
the Windows/iOS build split, and the distribution friction on day one, to buy a capability the v1
usage pattern doesn't need, is paying up front for a Phase 4 feature.

There is also a sequencing argument: **the PWA can be deployed and road-tested in an afternoon.** The
single most valuable thing this project can do right now is get two phones on a real road (HZ-8), and
the PWA gets there fastest.

### Native Swift + Kotlin

Best possible performance, battery, and background behaviour. Rejected on effort: two codebases, two
languages, and — per `docs/SYSTEM_DESIGN.md` §4 — the team already knows TypeScript, so Go is meant to be
the *only* new language.

### Flutter

One codebase, excellent performance, good map and WebRTC plugin ecosystems. Rejected for the reason
recorded in `docs/SYSTEM_DESIGN.md` §8: **Dart would be a second new language on top of Go.** The
one-new-language budget was already spent.

### PWA only, forever — abandon `mobile/`

Simplest possible answer: one client, one codebase, no native toolchain ever.

**Rejected**, but it's the closest call in this list. Two arguments kept `mobile/`:

1. **Background location is a real future requirement**, not a hypothetical. The moment someone wants
   to pocket their phone on a long ride, or ride with the screen off to save battery, the PWA cannot
   deliver — at any price, with any amount of engineering.
2. **The expensive part is already done.** The native permission and background config in
   `app.config.ts` is the piece `docs/SYSTEM_DESIGN.md` warns will eat real time, and it's written. Deleting
   `mobile/` would throw that away to save a directory.

The risk of keeping it — that `mobile/` rots as an unmaintained template — is real and is on the
board (BUG-08 already demonstrates it drifting). It's managed by treating `mobile/` explicitly as
deferred work with tasks attached, not as a live parallel client.

### Capacitor / Cordova — wrap the PWA natively

Genuinely clever: keep one web codebase, gain native background-location plugins. It would have given
us most of the PWA's iteration speed *and* the background capability.

Rejected because the WebView's `geolocation` behaviour under backgrounding is inconsistent across
platforms and OS versions, plugin quality for exactly the hard case (reliable background GPS with a
foreground service) is uneven, and it introduces a third client architecture to maintain alongside a
`mobile/` directory already configured for RN. If `mobile/` did not already exist with its native
config written, this would have been a stronger contender.

## Consequences

**Positive**

- **Instant iteration.** Vite HMR, no build step between a code change and a phone reload. Compare to
  an EAS build per native dependency change.
- **Distribution is a URL.** Share a link; tap "Add to Home Screen". No TestFlight, no sideloading,
  no store review, no Apple Developer account ($99/yr) or Google Play fee ($25) — the only money
  anywhere in this project (`docs/SYSTEM_DESIGN.md` §12), now avoided entirely.
- **The whole client is small.** Four components, four runtime dependencies, one 277-line stylesheet.
- **Real PWA polish already shipped:** manifest, service worker, iOS home-screen meta tags,
  safe-area insets, and **icons generated from code** by a hand-rolled PNG encoder using only
  `node:zlib` — so the repo carries zero binary assets.
- **The wake-lock implementation is correct**, including re-acquiring on `visibilitychange`, which the
  OS silently drops whenever the tab is hidden. Without that, the lock is lost on the first app-switch
  and never returns.
- **The backend was validated as client-agnostic** for free. Building the "wrong" client first proved
  the protocol has no browser or native assumptions in it.
- Phases 0 and 1 shipped on web, and `web/` is now a proven reference for the native port.

**Negative**

- **Foreground-only tracking, by design.** Screen off or tab hidden ⇒ GPS stops ⇒ the rider goes
  stale and vanishes. The wake lock is the *entire* mitigation.
- **And the wake lock can be silently refused** — user agents may decline on low battery, and
  `useWakeLock.ts:18` swallows the failure. A rider whose lock was denied has their screen sleep and
  disappears from the group with no warning to anyone (BUG-07). **This is the single scariest
  consequence of the PWA bet: the mitigation for the known limitation can fail invisibly.** HZ-22
  makes it visible.
- **Battery is worse than native would be.** `enableHighAccuracy: true, maximumAge: 0` is the most
  expensive geolocation configuration available, applied unconditionally, and the JS throttle drops
  fixes *after* the OS has already paid to acquire them. Native `timeInterval` would push throttling
  into the OS. Plus the screen is on continuously, which is the largest drain of all. A long ride will
  need external power.
- **HTTPS is mandatory, not optional.** Geolocation, wake lock, PWA install, *and* WebRTC all require
  a secure context. This is why deployment (HZ-7) must precede Milestone 2 — until then, every
  feature is validated in desk tabs rather than on phones.
- **iOS is the weak platform.** Safari ignores much of the manifest (hence the meta tags in
  `index.html`), Wake Lock support arrived late, and installed PWAs get less background latitude than
  on Android.
- **No ride persistence across reload**, and the code never enters the URL — reload ejects you to the
  lobby (HZ-9). A native app would have had navigation state for free.
- **The service worker uses `registerType: "autoUpdate"`**, so a new version can swap in silently —
  mid-ride (HZ-30).
- **`mobile/` risk of rot.** It is a stock template with pre-installed deps, and it has already
  drifted out of buildability (BUG-08).
- **Some work will be done twice.** The map layer, location layer, and UI are re-implemented for RN
  at Milestone 4. Mitigated by `types.ts` and the store porting unchanged.

## Trade-offs

| We gave up | We got |
|---|---|
| Background / screen-off location tracking | An afternoon from code change to a phone on a road |
| Native battery efficiency (OS-level GPS throttling) | Distribution by URL — no stores, no accounts, no fees |
| Guaranteed wake behaviour (a lock can be refused) | A validated, client-agnostic backend, proven by accident |
| Native map and audio performance | A four-dependency client that a stranger can read in an hour |
| Navigation and persistence for free | Phases 0 and 1 shipped, on real devices, immediately |

**The bet in one sentence:** the phone is mounted with the screen on, so the browser's one real
limitation never applies — and we buy iteration speed and zero-friction distribution in exchange.
**The bet's weak point is that the wake lock can fail silently**, which converts a known limitation
into an unknown one. That is why HZ-22 exists.

## Future Revisions

This ADR is **explicitly time-boxed**. Milestone 4 ([`docs/ROADMAP.md`](../ROADMAP.md#milestone-4--native-experience))
exists to revisit it.

Move to native when any of these becomes true:

- **A rider wants to pocket the phone**, or ride screen-off to conserve battery. This is the primary
  trigger and it needs no further justification — the PWA cannot do it at any price.
- **Wake-lock refusals cause real rides to break.** HZ-22 will tell us how often it happens. If it's
  common on real hardware, the mitigation has failed and the bet is lost.
- **Battery measurements from HZ-8 are unacceptable** even with external power.
- **Rides get long enough that foreground-only is impractical** — a multi-hour ride where the screen
  must sleep.

**Migration path, in dependency order** (HZ-17, HZ-19):

1. Fix the config drift so a dev client can build at all (HZ-4 — already on the board).
2. Resolve the `features/` vs flat directory question (HZ-18) *before* porting.
3. Port in order: `types.ts` → store → socket → config/identity (AsyncStorage) → location → map →
   standings UI. Types and store copy unchanged; the socket needs only its identity backend swapped.
4. Replace `useGeo` with `Location.watchPositionAsync` (throttling moves into the OS — strictly
   better) and **delete `useWakeLock` outright**, replaced by real background modes.
5. Solve the hard problem explicitly (HZ-19): **a background task runs in a separate JS context and
   cannot reuse the React-owned WebSocket.** Decide in an ADR whether the socket moves outside React
   or fixes are queued and handed off. `docs/SETUP_MOBILE.md:249` glosses over this; it is the hardest
   unsolved design question in the project.

**Both clients are expected to coexist**, not for one to replace the other. The PWA stays the
zero-friction way for a new rider to join a ride from a link. The native app is for people who ride
often enough to install it.

**What would *not* justify moving early:** wanting nicer animations, native-feeling navigation, or
app-store presence. Those are not the reason `mobile/` exists.
