# ADR-002: WebSockets, not REST polling, for live state

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-07-28 *(records a decision made during initial design; see `docs/SYSTEM_DESIGN.md` §5.2, §8)* |
| **Deciders** | Horizon team |
| **Supersedes** | — |

## Context

Every rider produces a GPS fix roughly once per second and needs to see everyone else's position
with sub-second freshness. At bike speeds (~20 km/h ≈ 5.5 m/s), a second of staleness is about 5.5
metres of positional error — fine. Ten seconds is 55 metres — not fine, that's the wrong side of an
intersection.

So the transport must carry:

- **Bidirectional traffic.** Riders push fixes *up* and receive group state *down*, continuously and
  independently. This is not request/response.
- **~1 Hz up, ~4 Hz down**, per rider, for the duration of a ride — potentially hours.
- **Small frames.** A `loc` message is ~100 bytes; a `state` frame with 15 riders is a couple of
  kilobytes.
- **Hostile network conditions.** Riders are on mobile data. Tunnels, dead zones, and handoffs
  between cell towers are routine, not exceptional.
- **A battery budget.** The phone is already running high-accuracy GPS and a screen wake lock.

And it must do this while the client is a browser today ([ADR-004](./ADR-004.md)) and a React Native
app later — with **no backend changes** between the two.

## Decision

**We use a single WebSocket per rider, opened at `GET /ws?ride=<code>&name=<name>&rider=<id>`.**

The protocol is deliberately minimal — three message types, defined in `CLAUDE.md` and mirrored in
`web/src/types.ts`:

| Direction | Type | Rate | Purpose |
|---|---|---|---|
| Client → server | `loc` | ~1 Hz | One GPS fix |
| Server → one client | `welcome` | once, first frame | The rider's assigned id, so it can find its own dot |
| Server → all in room | `state` | 4 Hz, unconditional | Complete snapshot of every rider |

Four properties are load-bearing and were chosen deliberately:

1. **Ingest and fan-out are fully decoupled.** No `loc` triggers a broadcast. A fixed 250 ms ticker
   sends unconditionally. **N riders at 1 Hz produce exactly 4 frames/second to each client,
   regardless of N** — the central scaling decision (`docs/SYSTEM_DESIGN.md:303`). Burst arrivals cannot
   amplify.
2. **Every `state` frame is a complete snapshot.** No deltas, no sequence numbers, no acks, no
   replay. A dropped frame costs 250 ms of freshness and nothing else, which is what makes property 3
   safe.
3. **Backpressure is drop, never block.** Each client has a 16-slot buffered send channel. If it's
   full, the frame is dropped for that client. A rider on a bad link degrades alone; the room never
   stalls.
4. **REST handles everything that isn't live state.** `POST /rides` (mint a code),
   `POST /rides/{code}/route` (ORS proxy), `POST /rides/{code}/voice-token` (LiveKit JWT),
   `GET /healthz`. These are one-shot, request/response, and cacheable-shaped — WebSocket would be
   the wrong tool.

The split is the point: **WebSocket for the continuous stream, REST for discrete operations.**

## Alternatives Considered

### REST polling (`GET /rides/{code}/state` every second)

**Genuinely attractive.** The simplest thing that could possibly work. No connection state, no
reconnect logic, no keepalive, no upgrade handshake. Trivially debuggable with `curl`. Traverses
every proxy, captive portal, and corporate firewall on earth. Horizontally scalable with zero
effort — any instance can serve any request. Honestly, at 15 riders it would have *worked*.

**Why it lost:**

1. **The uplink has no good home.** Riders must push fixes at 1 Hz. That means a `POST` per fix —
   with TCP and TLS handshake overhead per request unless connections are kept alive, and a second
   request stream layered on top of the polling one. Two independent request streams per rider is
   strictly worse than one socket carrying both directions.
2. **Latency floor.** Polling at 1 Hz means average staleness of 500 ms *on top of* the fix age.
   Polling faster multiplies the request count.
3. **Request amplification.** 15 riders polling at 1 Hz plus posting at 1 Hz is 30 requests/second
   with full HTTP headers each, against 15 sockets carrying ~100-byte frames. On mobile data, the
   header overhead alone exceeds the payload.
4. **Battery.** Each poll wakes the radio. A radio that never fully idles is a meaningful drain on a
   device already running high-accuracy GPS — see `docs/SYSTEM_DESIGN.md` §10 on battery being a known
   sharp edge.
5. **No natural liveness signal.** Detecting "this rider is gone" from polling requires a
   server-side timeout heuristic. A WebSocket close is unambiguous and immediate — which is exactly
   how riders are removed from a room today.

### Server-Sent Events (SSE) downstream + REST upstream

Real streaming downstream over plain HTTP, auto-reconnect built into `EventSource`, simpler than
WebSocket and firewall-friendly. This was the closest runner-up.

**Why it lost:** SSE is unidirectional, so the uplink still needs POSTs — back to two streams per
rider. `EventSource` has no binary frames and no built-in ping/pong. And critically, **React Native
has no built-in `EventSource`**, so the mobile client would need a polyfill or a different transport
— violating P7 ("every feature works for both web and mobile") and the
"backend requires zero changes for mobile" property.

### WebRTC data channels (peer-to-peer)

Lowest possible latency, no server in the media path, and we're already adopting WebRTC for voice
([ADR-005](./ADR-005.md)) so the machinery would be present.

**Why it lost decisively:** P2P is O(N²) connections, needs STUN/TURN (TURN is bandwidth-expensive
and card-required at any scale), and NAT traversal fails often enough on mobile networks to need a
fallback anyway. Fatally, **it has no authoritative node** — and
P1 ("the backend is the source of truth") and
P2 ("clients never calculate standings") require a single computation
of standings. Peer-to-peer would mean every client computing its own answer and disagreeing.

### MQTT over WebSocket

Purpose-built pub/sub for exactly this telemetry shape, with QoS levels and retained messages. Needs
a broker (another service to run, and free managed brokers require accounts and have limits), and
adds a protocol layer whose features we don't need — we have three message types and no delivery
guarantees to negotiate. All cost, no benefit at this scale.

### gRPC bidirectional streaming

Strong typing, code generation from a single `.proto` — **which would have solved the protocol
duplication problem that [ADR-001](./ADR-001.md) explicitly accepted as a cost.** Tempting.

Rejected because gRPC-Web requires a proxy (Envoy) for browsers, doesn't support client streaming
over gRPC-Web at all, and adds a substantial dependency and a build step to a backend with one
dependency (P5 ("keep dependencies minimal")). The type-safety win is
real; the operational cost is disproportionate at this scale.

### Long polling

Works everywhere, no new protocol. But it's strictly worse than SSE downstream (a request per
message), still needs a separate uplink, and holds a server connection per client anyway — paying
WebSocket's connection cost without WebSocket's efficiency.

## Consequences

**Positive**

- **One connection per rider carries everything**, in both directions, with ~100-byte frames and no
  per-message HTTP headers.
- **Constant message rate per client regardless of group size.** This is the property that makes 15
  riders and 5 riders cost the same.
- Disconnect detection is immediate and unambiguous — the socket closing *is* the signal.
- **The transport is identical for web and native.** Both use the global `WebSocket`; React Native
  provides it. The Go backend requires literally zero changes for the mobile client — the single
  strongest validation of P7 ("every feature works for both web and mobile").
- Protocol-level ping/pong (54 s ping, 60 s deadline) gives liveness for free; browsers auto-respond
  to pings at the protocol level, so the client needs no heartbeat code.
- Snapshot semantics make the whole system tolerant of loss: drop-on-full is safe, reconnection needs
  no replay, and there is no gap-recovery logic anywhere.
- The `[state]` frame is marshalled **once** per tick and the same byte slice is sent to every
  client — O(R) sends but O(1) serialization.

**Negative**

- **WebSocket handshakes are exempt from CORS.** This directly caused BUG-05 to hide for as long as
  it did: `POST /rides` was silently broken while the join path worked perfectly, so the pipe
  appeared healthy. It also means `CheckOrigin` is the *only* origin defence — and it currently
  returns `true` for everything (BUG-04). **The transport choice moved a security control from the
  browser to our code, and we haven't implemented it yet.**
- **Reconnect logic is ours to write.** Exponential backoff (1→15 s, no jitter — HZ-39), an
  intentional-close guard, and status states all live in `net/ws.ts`. Polling would have needed none
  of it.
- **Connection state is server memory.** Rooms live in a Go map, so a process restart destroys every
  ride. Acceptable (clients repopulate in seconds) except for routes, which no client re-POSTs —
  HZ-35.
- **Stateful connections block trivial horizontal scaling.** Two instances share nothing; a rider on
  A cannot see a rider on B. Documented and accepted; Redis Pub/Sub is the escape hatch.
- **Some corporate proxies, hotel Wi-Fi, and captive portals break long-lived WebSockets.** We have
  no fallback transport and no diagnostic to distinguish "blocked" from "server down" (RISK-N5).
  Polling would have been immune.
- **Fixes generated while the socket is down are silently discarded** (`ws.ts:70`) — no queue, no
  replay, no user-visible indication (HZ-43).
- Debugging needs a WebSocket client; `curl` is not enough. This is why `backend/wstest.mjs` exists.

## Trade-offs

| We gave up | We got |
|---|---|
| Trivial debuggability with `curl` | One bidirectional connection instead of two request streams |
| Automatic CORS protection on the live path | Sub-second latency at ~100 bytes/frame |
| Stateless servers and trivial horizontal scale | Constant per-client message rate regardless of group size |
| Free reconnect (the browser retries a failed poll) | Immediate, unambiguous disconnect detection |
| Universal proxy/firewall traversal | Identical transport for web and native, zero backend changes |
| Survival across a server restart | Meaningfully lower battery and data use |

**Latency budget, accepted explicitly:** up to 1000 ms client throttle + ≤250 ms tick + 2× network
RTT. At bike speeds that's roughly 7 m of worst-case positional error — irrelevant for the use case,
and cheap insurance against message amplification.

## Future Revisions

Revisit if:

- **Real riders hit proxy or captive-portal failures.** The fix is a fallback, not a replacement: try
  WebSocket, fall back to SSE-plus-POST, and surface which transport is active. Only build this if
  HZ-8 (the road test) or later rides actually produce the failure.
- **A ride needs more than one server process.** Add Redis Pub/Sub between instances
  (`docs/SYSTEM_DESIGN.md` §9). The transport doesn't change; only the fan-out does.
- **Group size grows past ~50.** Then per-client filtering matters — viewport culling, delta
  encoding, or dropping to 2 Hz. Every client currently receives a byte-identical full snapshot,
  which is correct at 15 and wasteful at 500.
- **Protocol drift causes a real bug** (DEBT-H7). The answer is a conformance test, or possibly
  revisiting gRPC/protobuf — but only if a shared schema is the *only* remaining fix.
- **Battery measurement shows the socket is a meaningful drain.** Unlikely — GPS and the screen
  dominate — but HZ-8 will produce the numbers. If so, lower the tick rate before changing transport.

**What would *not* justify revisiting:** having to write reconnect logic, or wanting to debug with
`curl`. Both were known costs.
