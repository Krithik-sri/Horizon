# ADR-016: Anonymous sign-in is the default identity — an account is an upgrade, never a gate

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-10 |
| **Deciders** | Horizon team |
| **Supersedes** | — |
| **Amends** | — (resolves a question [ADR-008](./ADR-008.md) left open: it named Supabase Auth the only issuer of identity without saying what a rider does before they have one) |

## Context

`ADR-008` was unambiguous about where identity comes from:

> "Supabase Auth is the *only* issuer. The Go server **verifies** Supabase JWTs — it never mints
> identity, never has a user table, never invents a session."

The app has never talked to Supabase. What exists instead is `mobile/src/core/riderId.ts`: a UUID
minted on first launch and kept in AsyncStorage, plus a display name. That is enough for the one job
it was built for — giving `backend/internal/hub/hub.go` a stable key so a reconnect replaces a
rider's old connection instead of adding a ghost — and it has served that job correctly.

It is not an identity. It cannot own a row, cannot be verified by anything, and dies with the
install. Everything in `docs/PRODUCT.md`'s Return register — the journal, the photos, the ride
history — needs a subject that outlives an app reinstall and that Postgres can enforce access
against. So the question `ADR-008` never had to answer becomes blocking: **what is a rider before
they have an account?**

The obvious answer is "make them sign up," and it is wrong for this product. `docs/PRODUCT.md` gives
Departure exactly one question — *"Am I ready to ride?"* — and an email verification step is a
different question asked at the worst possible moment, at a petrol stop, in gloves, on mobile data.
The current flow is: type a name, tap "Start a ride." Anything that adds a step to that is a
regression regardless of what it enables later.

## Decision

### 1. Every rider is signed in anonymously, at first launch, invisibly

`signInAnonymously()` runs once behind the splash screen `mobile/src/app/_layout.tsx` already holds
for font loading. Every subsequent launch reads a cached session from AsyncStorage with no network
call. **The Departure flow does not change by one tap.**

An anonymous user is a real Supabase user, not a placeholder: it carries `role: "authenticated"`,
`aud: "authenticated"`, a stable `sub`, and `is_anonymous: true`. `auth.uid()` works, and policies
written `to authenticated` apply to it. Row-Level Security therefore needs no special case for the
anonymous majority, which is the property that makes this workable at all.

### 2. Upgrading to a real account preserves `sub`

`supabase.auth.updateUser({ email })` plus an OTP converts an anonymous user in place. **The `sub`
does not change**, so every row already written keeps working with no migration and no backfill.

This is the entire reason to prefer this over the per-install UUID the app already has. Both give a
stable id today. Only one of them still works on the day accounts ship — the other requires
rewriting every row keyed on an identifier that, by then, means nothing.

### 3. The rider id becomes the JWT `sub`; `riderId.ts` is deleted

The client stops minting and stops sending an id. `ADR-017` covers the server side and the protocol
change.

`saveRiderName` / `loadRiderName` survive, moved to `mobile/src/core/riderName.ts`, still in
AsyncStorage. The display name is deliberately **not** put in `user_metadata`: it would cost a
network round-trip on the screen whose job is to be instant, to store a value that is cosmetic and
per-ride. It also serves the deep-link and remount rejoin path in `ride/[code].tsx`, which must work
offline. Move it when a real profile screen exists and there is something else to put beside it.

### 4. Two packages, both JS-only

`@supabase/supabase-js` and `react-native-url-polyfill`. No dev-client rebuild — which is why this
phase can land between two that do need one.

The already-installed `@react-native-async-storage/async-storage` is the session store; it is
already the storage layer `riderId.ts` uses. Deliberately **not** added: `expo-sqlite` (Expo's
Supabase guide uses its `localStorage` shim as the auth adapter, but AsyncStorage is already here),
`base64-arraybuffer` (SDK 56's `File.bytes()` returns a `Uint8Array` that Storage uploads accept
directly), `expo-crypto` (nothing needs it once `getRiderId()` is gone).

Four setup details that are each a wasted hour if missed, recorded because none is discoverable from
the code:

- `import 'react-native-url-polyfill/auto'` must be the **first line** of `core/supabase.ts`. Hermes
  has no `URL.hostname`, and supabase-js throws on import without it.
- `detectSessionInUrl: false` — there is no browser URL to parse.
- `AppState` auto-refresh must be wired. Without it the refresh timer stops when the app
  backgrounds, which is where a phone spends most of a ride, and the *next reconnect* fails rather
  than the current one — a failure that looks like a networking bug and is not.
- **Anonymous sign-ins are off by default** in the Supabase dashboard and must be enabled.

### 5. The anon key in the app bundle is not a secret

`EXPO_PUBLIC_SUPABASE_ANON_KEY` ships inside the APK and that is by design — it is a publishable
key, present in every Supabase client app ever built, and **RLS is the security boundary, not key
secrecy**. `CLAUDE.md` hard constraint #4 concerns `SUPABASE_JWT_SECRET`, which stays in
`backend/.env` and never reaches the client.

This is written down because it looks exactly like a violation to anyone reading quickly, and the
"fix" — moving the key server-side — would break the client for no gain. It belongs as a comment in
`.env.example` too, not only here.

## Alternatives Considered

### Require email sign-up before a ride

The honest upside: one identity model instead of two, no anonymous-user accumulation, and a rider
who reinstalls keeps their history. **Rejected** as a direct product regression — it inserts a
verification step into the one flow `docs/PRODUCT.md` reserves for "am I ready to ride?", and it
gates a group ride on the slowest rider's inbox.

### Keep the per-install UUID and write to Postgres with the service key

No auth system at all, and it ships fastest. **Rejected** immediately: the service-role key bypasses
RLS entirely, and putting it in the APK hands every user full read/write over every other user's
data. This is `CLAUDE.md` hard constraint #4 in its clearest form.

### Have the Go server mint identity

The Go server already holds a signing secret and already knows every rider in a room, so minting
would be a small amount of code. **Rejected:** `ADR-008` reserves issuance to Supabase Auth in a
single sentence written specifically to prevent this, and a Go-minted token could not be verified by
Postgres RLS, which is the only place identity actually needs to be enforced.

### Ship the local UUID now, add Supabase when accounts are actually needed

Genuinely tempting under a do-less rule: it defers a whole subsystem, and Return is still unbuilt.
**Rejected** because the deferral has a compounding cost rather than a flat one. Every ride, journal
entry and photo written before the switch would be keyed to a per-install UUID with no relationship
to the eventual `sub`, so the migration is not "add auth later" but "add auth later *and* reconcile
every row against an identifier that never meant anything." Doing it once, before there are rows, is
strictly cheaper.

### Store the display name in `user_metadata`

One source of truth for who a rider is, and it would survive a reinstall alongside everything else.
**Rejected** for now on latency: Departure would wait on a network round-trip to render a name that
is cosmetic. Revisit with a profile screen, per Decision §3.

## Consequences

**Positive**

- The frictionless Departure flow is preserved exactly — this record buys durable identity for zero
  taps.
- RLS needs no anonymous special case; `auth.uid()` is meaningful for every rider from first launch.
- Accounts become a genuinely additive feature later, with no data migration.
- One identity concept replaces two, and `riderId.ts` is deleted rather than kept in parallel.

**Negative**

- **Supabase becomes a hard dependency for starting a ride.** Free-tier projects pause after a week
  of inactivity, and a paused project now means the app cannot start a ride at all. That is a new
  single point of failure in a system that previously needed only the Go server. Mitigation is a
  weekly ping to `/auth/v1/health`, or accepting it knowingly — but the symptom must be recognisable
  when it happens.
- **First-ever launch requires network.** No session, no ride. This needs a real message, not a
  spinner that never resolves.
- **Uninstall means the data is gone permanently.** An anonymous user has no recovery path by
  definition. This must be surfaced once, quietly, in the Return register — one line of
  `type.reflective.caption`, never a badge, never repeated, and never a prompt to "secure your
  account."
- **Anonymous users accumulate in `auth.users`** with no automatic cleanup. Irrelevant at this scale;
  a `pg_cron` sweep of anonymous users with zero rides older than 30 days if it ever isn't.
- Anonymous sign-in is rate-limited to 30 signups/hour/IP, which is invisible in normal use and
  confusing on a shared network during testing.

## Trade-offs

| We gave up | We got |
|---|---|
| A single identity model (anonymous *and* account, rather than just account) | A Departure flow that still costs one tap |
| Independence from Supabase for the core riding loop | Durable identity that RLS can enforce, from first launch |
| Deferring the whole auth subsystem until Return needs it | No migration of rows keyed to an identifier that would have stopped meaning anything |
| A display name that survives reinstall | A Departure screen that renders without waiting on the network |

## Future Revisions

Revisit if:

- **Riders lose data to reinstalls often enough to matter.** The answer is prompting for account
  upgrade at a *considered* moment in the Return register — never in Departure, never mid-ride.
- **The free tier's inactivity pause bites in the field.** Either the keep-alive ping or a paid
  tier, which would be the first spend and therefore an ADR against `ADR-006`.
- **A profile screen ships**, at which point the display name should move to `user_metadata`
  (Decision §3).
- **Anonymous user rows become a real cost**, per the cleanup note above.

**What would *not* justify revisiting:** wanting one identity model for tidiness. Two paths that
converge on the same `sub` is the design, and the anonymous path is the one almost every rider will
use.
