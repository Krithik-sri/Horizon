# ADR-005: LiveKit for voice, not custom WebRTC

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-07-28 *(records a decision made during initial design; see `docs/SYSTEM_DESIGN.md` §4, §5.3)* |
| **Deciders** | Horizon team |
| **Supersedes** | — |

## Context

Voice is one of Horizon's three stated product goals (`docs/SYSTEM_DESIGN.md` §1): live, walkie-talkie
style push-to-talk between riders in a group.

What that requires:

- **Group audio, up to ~15 participants**, in one room per ride.
- **Push-to-talk semantics** — publish the microphone only while a button is held; stay subscribed to
  everyone else's audio continuously.
- **Low latency**, over mobile data, at speed, while GPS and the map are already running.
- **Both clients** — browser today, React Native later ([ADR-004](./ADR-004.md)) — from one design.
- **Free, no credit card** ([ADR-006](./ADR-006.md)).

Realtime audio is a fundamentally different problem from realtime location. Location is small JSON
snapshots over one WebSocket, lossy by design, at 4 Hz ([ADR-002](./ADR-002.md)). Audio is continuous
media requiring jitter buffering, echo cancellation, noise suppression, codec negotiation,
packet-loss concealment, adaptive bitrate, and NAT traversal — none of which we have any interest in
implementing.

**The architecture is why it's separable.** `docs/SYSTEM_DESIGN.md` §1 describes exactly three wires out
of a rider's phone: map tiles, realtime state, and voice media. They are deliberately independent.
Voice can be added, removed, or fail entirely without touching the location pipe — which is precisely
why it's deferred to Milestone 3 rather than built alongside the core.

**The scaling constraint that rules out peer-to-peer:** a full mesh of 15 participants is 105
connections, each phone encoding and uploading 14 separate audio streams. That is untenable on mobile
data and on a phone battery. Group voice past about 4 participants needs an **SFU** (Selective
Forwarding Unit) — each client uploads once, the server forwards to everyone.

Building an SFU is, per `docs/SYSTEM_DESIGN.md` §4, *"a multi-month rabbit hole — avoid."*

## Decision

**We use LiveKit** — LiveKit Cloud's free tier for the SFU, `livekit-client` in the browser and
`@livekit/react-native` on native.

Design, per `docs/SYSTEM_DESIGN.md` §5.3:

- **The LiveKit room name is the ride join code.** The voice group and the location group line up
  automatically with no extra membership tracking. One identifier, two systems.
- **The Go backend mints the join JWT** via `POST /rides/{code}/voice-token`, using the LiveKit
  server SDK and `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` from env. **The secret never touches a
  client** ([P8](../DEVELOPMENT_GUIDE.md#p8--secrets-never-leave-the-server)). This is the same
  pattern as the ORS proxy in [ADR-003](./ADR-003.md).
- **Push-to-talk is `setMicrophoneEnabled(true/false)`** on button down/up. Always subscribed to
  others; connect with `audio: false` so the mic starts muted.
- **Voice media never passes through the Go server.** It goes phone ↔ LiveKit directly. Our backend
  is only an authorization authority.

Standing rule in `CLAUDE.md`: *"Don't roll custom WebRTC — voice goes through LiveKit."*

## Alternatives Considered

### Raw WebRTC, peer-to-peer mesh

No server, no vendor, lowest possible latency, and the browser APIs are built in. For two or three
riders it would genuinely work.

**Rejected decisively.** O(N²) connections: 15 riders is 105 peer connections, with each phone
encoding and uploading 14 streams. Mobile upload bandwidth and battery both fail well before that.
It also still needs STUN and — when symmetric NAT defeats hole punching, which is common on mobile
carriers — **TURN, which relays all media and is bandwidth-expensive and card-required at any real
scale.** So "no server" is an illusion; you need infrastructure anyway, just worse infrastructure.

### Self-hosted SFU (mediasoup, Janus, Jitsi, or LiveKit self-hosted)

Full control, no vendor, no usage limits. mediasoup and Janus are excellent. **LiveKit self-hosted
is the same software as the cloud tier and is written in Go** — the same language as our backend
([ADR-001](./ADR-001.md)).

**Rejected for v1 on hosting cost, not technical merit.** An SFU needs a real server with real
bandwidth — media relay is the opposite of cheap — plus TURN, TLS certificates, and operational
attention. [ADR-006](./ADR-006.md) forbids paid infrastructure, and our entire backend currently runs
as one 340-line binary on a free tier.

**This is explicitly the escape hatch**, and it is a good one: because we chose LiveKit Cloud rather
than a proprietary API, self-hosting is a **URL and credentials change**, not a rewrite. That
property is a large part of why LiveKit won.

### Agora

Mature, excellent quality, simple SDKs, and a genuinely generous free tier (10,000 minutes/month).
Probably the easiest integration in this list.

**Rejected:** proprietary and closed-source, so there is no self-hosting escape hatch — if the free
tier changes, the only options are paying or rewriting. A card is required past the free tier. And it
would be a permanent vendor lock on a core product feature, which is exactly the dependency shape we
avoided in [ADR-003](./ADR-003.md).

### Twilio Programmable Voice / Video

Rock-solid, superb documentation. **Requires a credit card up front.** Disqualified by
[ADR-006](./ADR-006.md) before any technical evaluation.

### Daily.co, Whereby, 100ms

All good managed WebRTC platforms with free tiers. All proprietary, all card-required past the free
tier, none self-hostable. Same objection as Agora.

### Jitsi Meet (public `meet.jit.si`)

Free, open source, no account. Rejected: the public instance is a *meeting* product, not an SFU SDK —
embedding it means an iframe with a UI we don't want, no clean push-to-talk primitive, and using a
donation-funded meeting service as an API is outside its intended use. Self-hosted Jitsi is the
"self-hosted SFU" option above.

### Audio over the existing WebSocket

Tempting for its apparent simplicity: we already have a socket to the Go server
([ADR-002](./ADR-002.md)), so stream Opus frames over it and fan them out like `state` frames.

**Rejected, and worth explaining because it looks reasonable.** TCP is the wrong transport for
realtime audio — head-of-line blocking means one lost packet stalls the entire stream, where WebRTC's
UDP transport simply drops it and conceals the gap. We would also have to implement jitter buffering,
echo cancellation, noise suppression, packet-loss concealment, and adaptive bitrate ourselves. And it
would put continuous media through our single Go process, coupling voice failures to location
failures — destroying the three-independent-wires property that makes voice deferrable in the first
place. This option trades a well-solved problem for several unsolved ones.

### No voice at all

Riders have phones; group calls exist. Genuinely worth asking.

Rejected because push-to-talk while riding is materially different from a phone call: hands stay on
the bars, it's one-to-group rather than one-to-one, and it doesn't occupy the phone. It's one of the
three product goals. But note it is **correctly the last feature to build** — it's the only one fully
independent of the location pipe, so it's the safest thing to defer.

## Consequences

**Positive**

- **We don't build an SFU.** The single largest scope reduction in the project.
- **Zero cost on the free tier**, no credit card, email signup only.
- **Open source, with a real self-hosting path.** Not a lock-in. Migration is a URL and credentials
  change.
- **LiveKit's server is written in Go**, so self-hosting later keeps us in one operational ecosystem
  ([ADR-001](./ADR-001.md)).
- **One design, both clients.** `livekit-client` (web) and `@livekit/react-native` (native) share
  concepts and API shape. The token endpoint is identical for both
  ([P7](../DEVELOPMENT_GUIDE.md#p7--every-feature-works-for-both-web-and-mobile)).
- **Room name = join code** means voice membership needs no separate tracking, no invitations, and no
  synchronization with the location room. Joining the ride *is* joining the voice room.
- **Voice media never touches our backend**, so audio load doesn't compete with the location pipe and
  a LiveKit outage degrades voice only — dots, standings, and the map keep working.
- The native config is **already written**: the LiveKit Expo plugin with `audioType: "communication"`,
  `@config-plugins/react-native-webrtc`, `NSMicrophoneUsageDescription`, and
  `UIBackgroundModes: ["location","audio"]` are all in `mobile/app.config.ts`.

**Negative**

- **A third-party dependency on a core product feature.** If LiveKit Cloud is down, voice is down.
- **The free tier can change.** It is a company's commercial decision, not a contract with us. The
  self-hosting hatch is the mitigation, and it costs money to exercise.
- **First new backend dependency since `gorilla/websocket`.** The LiveKit Go server SDK is
  substantially larger than our current dependency, taking the backend from one dependency to two —
  a real cost against [P5](../DEVELOPMENT_GUIDE.md#p5--keep-dependencies-minimal). Justified
  because minting a JWT by hand with the right claims is exactly the kind of security-sensitive code
  we should not hand-roll.
- **The token endpoint inherits every auth weakness in the system.** It will mint a room-join JWT
  based purely on a claimed rider id and a ride code that — until HZ-3 — isn't validated at all.
  **This is the first place our "the join code is the entire access-control model" stance produces a
  cryptographically signed credential to an external service** (RISK-S7). HZ-15 must depend on HZ-3
  and use a short TTL.
- **WebRTC requires a secure context**, adding to the list of reasons HTTPS deployment (HZ-7) must
  precede feature work.
- **iOS requires a user gesture to start audio.** Voice must be gated behind an explicit "Join voice"
  tap; it cannot auto-connect (`docs/SETUP_WEB.md:170`).
- **Battery.** Continuous WebRTC audio stacks on top of continuous high-accuracy GPS and a
  screen-on wake lock ([ADR-004](./ADR-004.md)). This is the heaviest combination the app will ever
  run, and it is unmeasured — HZ-37 exists to measure it *before* tuning.
- **Native WebRTC is a heavy dependency.** `@livekit/react-native-webrtc` significantly increases app
  size and dev-client build time, and any upgrade forces a rebuild.

## Trade-offs

| We gave up | We got |
|---|---|
| Full control over the media stack | Months of SFU engineering we will never do |
| Independence from a third party on a core feature | Zero cost, zero card, working group voice |
| Backend dependency count (1 → 2) | Correct, security-sensitive JWT minting we didn't hand-roll |
| Simplicity — a whole second realtime system | Voice failures fully isolated from location failures |
| App size and dev-client build time on native | An open-source escape hatch that is a config change, not a rewrite |

**The governing principle**, from `docs/SYSTEM_DESIGN.md`: *don't build what you can rent — and prefer
free/open where it exists.* We rent tiles ([ADR-003](./ADR-003.md)) and voice so we can afford to
build the one thing that is genuinely ours: the realtime location server.

## Future Revisions

Revisit if:

- **LiveKit Cloud's free tier no longer covers usage.** Self-host LiveKit — same software, Go, and
  the client change is a URL plus credentials. Budget a small VPS; this is the first thing in the
  project that would cost money, and it would require revisiting [ADR-006](./ADR-006.md).
- **LiveKit Cloud proves unreliable in real rides.** Measure during HZ-8 and HZ-16 testing. Same
  remedy: self-host.
- **Group size grows past the free tier's participant or minute limits.** Self-host.
- **Voice quality at speed is inadequate** — wind noise, road noise, one-handed operation. That's a
  tuning problem (noise suppression settings, codec bitrate, PTT ergonomics), not a platform problem.
  Do not change vendors over it.
- **The security model tightens.** Real auth would change what the token endpoint asserts, but not
  the choice of LiveKit.

**A hard rule regardless of any revision:** the LiveKit API secret stays server-side, and tokens stay
short-lived and minted per rider per ride. No revision of this ADR may move token minting to a client.

**What would *not* justify revisiting:** app size, dev-client build time, or wanting fewer backend
dependencies. All three were known and accepted here.
