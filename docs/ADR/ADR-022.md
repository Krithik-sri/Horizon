# ADR-022: The LiveKit token is signed with `golang-jwt`, not `livekit/protocol`

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-10 |
| **Deciders** | Horizon team |
| **Supersedes** | — |
| **Amends** | [ADR-020](./ADR-020.md) (Decision §4 → "Minted with `github.com/livekit/protocol/auth`") · [ADR-005](./ADR-005.md) (its "don't hand-roll a JWT" reasoning is reinterpreted, not overturned — see Decision §2) |

## Context

`ADR-020` §4 chose `github.com/livekit/protocol/auth` to mint voice tokens, on `ADR-005`'s
authority: *"minting a JWT by hand with the right claims is exactly the kind of security-sensitive
code we should not hand-roll."* That reasoning was sound when `ADR-005` was written, in a repo whose
only dependency was `gorilla/websocket`.

Two things have changed since.

**`golang-jwt/jwt/v5` is now a direct dependency.** `ADR-017` added it to verify Supabase tokens, and
`CLAUDE.md` mandates it by name for JWT work. The safe-library requirement `ADR-005` was protecting
is now satisfiable without adding anything.

**The cost was measured rather than assumed.** `livekit/protocol` brought **68 indirect modules** and
took `go.sum` from a handful of lines to 221 — protobuf, protovalidate, cel-go, antlr4, prometheus
client internals, and `pion/webrtc` — into a server that does no WebRTC, terminates no media, and
speaks no protobuf. It was imported for exactly two symbols: `VideoGrant` and `NewAccessToken`.

`ADR-020` itself already flagged part of this, having discovered that choosing `protocol/auth` over
`server-sdk-go` did not avoid `pion/webrtc` at all: `go mod why` reported
`backend → protocol/auth → protocol/utils → pion/webrtc/v4`.

## Decision

### 1. Build the claim struct in `backend/voice.go` and sign it with `golang-jwt`

A LiveKit access token is a plain HS256 JWT with a documented shape. Verified against
`livekit/protocol@v1.50.4`'s own source rather than from documentation or memory: `ToJWT` builds a
`tokenClaims{jwt.RegisteredClaims; ClaimGrants}` — `iss` = API key, `sub` = identity, `iat`/`nbf`/`exp`,
and a flattened `video` grant object — then calls
`jwt.NewWithClaims(jwt.SigningMethodHS256, claims).SignedString([]byte(secret))`.

That last line is `golang-jwt/jwt/v5`. **The library we now call directly is the library
`livekit/protocol` was calling on our behalf.** The 68 modules were the wrapper, not the crypto.

### 2. This is not hand-rolling in `ADR-005`'s sense

`ADR-005`'s concern was security-sensitive primitives: HMAC, base64url, constant-time comparison,
algorithm selection. None of that is written here. `voice.go` declares a struct with JSON tags and
hands it to the same vetted library `CLAUDE.md` already requires — the identical relationship
`internal/auth` has with it on the verification side, which `ADR-017` established without
controversy.

The distinction that matters: **`ADR-005` was protecting against writing crypto, not against
declaring a claim shape.** This record makes that reading explicit so the rule keeps its force where
it belongs.

### 3. The claim shape becomes our contract, and a test pins it

The real cost, stated plainly: the wire format is no longer maintained upstream on our behalf. If
LiveKit renames a grant field, nothing fails to compile — the token would simply be wrong.

`backend/voice_test.go` therefore asserts the **raw JSON payload as a map**, not a struct round-trip:
`iss`, `sub`, `iat`/`nbf`/`exp`, `video.room`, `video.roomJoin`, `video.canPublish`,
`video.canSubscribe`, `video.canPublishData`. A struct-based assertion would pass happily while
sending keys LiveKit ignores; reading the decoded payload as `map[string]any` is what catches a
rename.

### 4. `canPublishData` is asserted for presence, not only for value

The sharpest edge found in this swap, and the reason it was worth doing carefully.

LiveKit's own `VideoGrant` types the grant booleans as `*bool` with `omitempty` — deliberately, so an
unset grant is distinguishable from one explicitly set to `false`. **LiveKit's server treats an
omitted grant as permitted.** A naive port to plain `bool` with `omitempty` would drop
`canPublishData: false` from the payload entirely and silently grant every rider a data channel that
`ADR-020` §4 means to deny.

`voice.go` therefore uses plain `bool` with **no `omitempty`**, so all three grants always serialise,
and the test asserts the key is *present* as well as false. Plain-and-always-emitted makes the safe
thing the only representable thing — the same structural-enforcement approach `ADR-019` §4 uses for
`RideFacts`.

## Alternatives Considered

### Keep `livekit/protocol`

Upstream owns the claim shape, so a LiveKit format change arrives with a version bump rather than a
silent breakage — a real benefit, and the one thing this record gives up. **Rejected** on
proportionality: 68 modules and a WebRTC stack to avoid maintaining one struct of five documented
fields, in a backend whose stated value (`ADR-001`, `ADR-010`) is being small enough to reason about.

### Use `livekit/protocol` but vendor only `auth`

Go modules have no partial-import mechanism; `protocol/auth` imports `protocol/utils`, which is where
`pion/webrtc` enters. Not available.

### Hand-roll the HMAC signing too

Removes `golang-jwt` as well. **Rejected outright** — this is exactly what `ADR-005` forbids and it
remains forbidden. The dependency being cut is the wrapper, never the crypto library.

## Consequences

**Positive**

- Backend dependencies: **2 direct, 0 indirect**, `go.sum` 221 → 4 lines. This is precisely the state
  `ADR-008` predicted when it called `golang-jwt` "the second and last third-party Go dependency."
- `pion/webrtc`, protobuf, cel-go and antlr leave a server that never used them; build time, image
  size and supply-chain surface all shrink with them.
- Token minting and token verification now use one library, with one set of parse/sign conventions.

**Negative**

- **The LiveKit claim shape is now ours to maintain.** An upstream format change surfaces as voice
  failing to join, not as a compile error. Decision §3's test is the mitigation and it is not a
  complete one — it pins what we send, not what LiveKit currently expects.
- **Nobody here tracks LiveKit's changelog.** The claim shape has been stable for years, which is the
  bet being made; it is a bet.
- `ADR-020` §4's text now describes an implementation that no longer exists, corrected only by this
  record.

## Trade-offs

| We gave up | We got |
|---|---|
| Upstream ownership of the claim shape | 68 fewer modules, and no WebRTC stack in a server that does no WebRTC |
| A compile error if LiveKit renames a field | A test that asserts the actual bytes on the wire, including a grant whose absence would be a granted permission |

## Future Revisions

Revisit if:

- **Voice fails to join after a LiveKit platform update**, which is the failure mode this record
  accepts. The fix is a claim-shape diff against `livekit/protocol`'s current source, not a return to
  the dependency.
- **The server needs more of LiveKit than a join token** — egress, ingress, server-side room
  management, webhooks. At that point the module earns its weight and should come back wholesale.

**What would *not* justify revisiting:** discomfort at building a JWT claim struct by hand. Decision
§2 draws the line at crypto, and that line is unchanged.
