# ADR-010: One hub lock and one broadcast sweep

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-02 |
| **Deciders** | Horizon team |
| **Supersedes** | — |

## Context

Three bugs in `backend/internal/hub` turned out to be one design gap, not three independent fixes.

- **The ghost-rider bug.** `Room.rider` is `map[*Client]bool` — keyed by the connection, not the
  rider. A reconnect (mobile networks drop — `CLAUDE.md`) presents the same stable `rider` id but
  is a *new* `*Client`, so it gets seated beside its own zombie instead of replacing it. The zombie
  only leaves when its read pump's 60 s (`pongWait`) deadline finally fires. Every tunnel, every
  dead zone, every cell-tower handoff produces this, for up to a minute at a time.
- **The decorative join code.** `Hub.CreateRide()` is `return genCode()` — it mints a string and
  forgets it. `Hub.room(code)` creates a room for whatever code the *first* `/ws` client presents,
  minted or not, so `POST /rides` is a suggestion and any six-character guess joins a stranger's
  convoy. Codes came from `math/rand`, which is fine for uniqueness at this volume but was never
  the actual problem — the problem is that nothing checked the code against anything.
- **The room that never dies.** `Room.run()` has no exit path, and nothing ever deletes an entry
  from `Hub.rooms`. Every ride ever started holds a goroutine and a 250 ms ticker for the life of
  the process — a slow, permanent leak a dev server never runs long enough to notice.
- **Why one patch each doesn't work.** `Room.mu` guards two unrelated things at once — the rider
  *set* (who's in the room) and each client's *latest fix* (`lat`/`lng`/`lastSeen`) — and
  `readPump` blocks sending to an **unbuffered** `unregister` channel that only `Room.run`'s select
  loop drains. Garbage-collecting a room means deciding, from *outside* that room, that it's safe
  to stop draining those channels — while one client's `readPump` may be mid-send to `unregister`
  and another mid-send to `register`. Bolting GC onto the existing register/unregister/mutex hybrid
  is exactly the kind of change that deadlocks in production and passes every manual test. The
  three fixes had to be designed together, not patched one at a time.

## Decision

**One `sync.Mutex` on the `Hub`. One sweep goroutine for the whole process.**

Rooms stop owning any concurrency machinery of their own:

- `Room` becomes plain data: `riders map[string]*Client` (keyed by the stable rider id, not the
  connection) and `emptySince time.Time`. No goroutine, no `register`/`unregister` channels, no
  per-room mutex.
- `Hub.mu` — one `sync.Mutex` — guards every room's rider map *and* every client's
  `lat`/`lng`/`lastSeen`. There is exactly one lock in `internal/hub` now, not one per room plus a
  second one inside it.
- Keying `riders` by id makes the ghost-rider bug a map assignment instead of a policy decision: a
  reconnect with the same id overwrites the old entry in place, under the lock. There's no zombie
  left to time out.
- `Hub.CreateRide()` generates a code with `crypto/rand` and **reserves it immediately** — it
  creates the (empty) room under the lock before returning the code, instead of leaving
  room-creation to whichever client happens to show up first.
- `GET /ws` looks the code up under the lock **before** calling `upgrader.Upgrade`. An unknown or
  expired code gets `404 unknown ride code` and the connection is never upgraded — no socket opens
  and dies, no ambiguity client-side between "bad code" and "server down."
- Rider ids are also `crypto/rand` now, matching the codes — `math/rand` is gone from
  `internal/hub`.
- A single goroutine, started once when the process boots, replaces every per-room goroutine. On a
  fixed 250 ms tick it calls one function — `sweep(now)` — for the whole hub: broadcast `state` to
  every room exactly as before, and delete any room whose `emptySince` is more than `roomGrace`
  (5 minutes) in the past. Separating the ticker from `sweep(now)` means the GC logic takes a
  timestamp instead of reading the clock itself, so a test can call `sweep(fakeNow)` directly
  instead of waiting on a real ticker or a real 5 minutes.
- `emptySince` is set the moment a room's rider map goes empty — including "reserved but nobody
  ever joined," since a freshly created room is empty from the start. It is never cleared on join
  and does not need to be: the GC condition tests `len(riders) == 0` first, so the timestamp is
  only ever read while the room is genuinely empty. One field, one rule, covering both "minted but
  never used" and "everyone left."

## Relationship to ADR-002

This ADR does **not** supersede [ADR-002](./ADR-002.md), which stays **Accepted**. The wire
protocol is byte-for-byte unchanged, and all four of its load-bearing properties survive intact:

1. **Ingest and fan-out are still fully decoupled.** The sweep goroutine still broadcasts on a
   fixed 250 ms tick; no `loc` message ever triggers a broadcast.
2. **Every `state` frame is still a complete snapshot.** No deltas, no sequence numbers, no acks.
3. **Backpressure is still drop-never-block**, on the same 16-slot buffered `send` channel per
   client.
4. **REST still handles everything that isn't live state** — `POST /rides`, the route proxy, the
   voice-token endpoint, `GET /healthz`.

What changes is purely internal: *how* the hub is allowed to touch its own state, not what it
sends or when. ADR-002's decision section describes "one goroutine per join code" — that sentence
documented an implementation detail, not a load-bearing property, and this ADR replaces that
detail. A future reader hitting both documents should read them as sequential, not contradictory:
ADR-002 decided WebSockets over polling and sketched the first implementation; this ADR describes
how that implementation had to change to close three bugs. Nothing here reopens the transport
question.

## Alternatives Considered

### Patch each bug independently, keep the per-room goroutine

**The obvious first move**, and the one this ADR started from — it's the smaller diff, and it
leaves ADR-002's "one goroutine per join code" sentence true. Keying `Room.rider` by id instead of
`*Client` fixes the ghost-rider bug on its own. Making `CreateRide` pre-create the room fixes the
decorative-code bug on its own.

**Why it lost:** neither of those touches the actual blocker, which is GC. Deleting a room safely
requires deciding, from outside `Room.run`'s select loop, that no client is about to send on its
channels — and `Room.mu` already double-duties as both the rider-set lock and the per-client fix
lock. Adding a third responsibility (room lifecycle) to that hybrid is exactly where independent
patches stop being independent: the GC fix has to touch the same lock and the same channels the
other two fixes touch, which means designing all three together or shipping a deadlock.

### Sharded locks (N mutexes, room code hashed to a shard) instead of one hub lock

**Genuinely attractive**, and it's the eventual answer if this ever needs it — see Future
Revisions. Sharding caps lock contention regardless of room count, which a single mutex does not.

**Why it lost for now:** it's the more complex design — shard selection, a GC sweep per shard, N
locks to reason about instead of one — bought against a contention problem that doesn't exist yet.
At ≤15 riders per convoy and a handful of live rides, one mutex costs microseconds per broadcast
tick. Building the sharded version now would be solving a scale problem before it's real.

## Consequences

**Positive**

- Three bugs closed by construction, not by three separate patches: reconnect replaces in place,
  `POST /rides` is load-bearing, and empty rooms are actually collected.
- Fewer moving parts: no per-room goroutine, no `register`/`unregister` channels, no second mutex
  inside `Room`.
- Goroutine count is now **O(connections)**, not **O(connections + rooms)** — a room with no
  current riders costs nothing but a map entry until it's swept.
- Splitting the ticker from the work (`sweep(now)`) makes GC testable with a synthetic clock
  instead of a real 5-minute sleep in a test suite.

**Negative — an accepted ceiling, not a hidden one**

- **One lock guards every room.** `broadcast` marshals JSON for a room's `state` frame while
  holding `Hub.mu`. At ≤15 riders per convoy and a handful of concurrent rides that's microseconds
  of hold time per tick — but it is a real ceiling, not a free lunch. If concurrent rides ever
  reach the hundreds, this is the first thing to shard: one lock per room (or per shard of rooms)
  instead of one lock for the whole hub.

**Still open after this ADR**

- The sweep goroutine and both connection pumps (`readPump`, `writePump`) run outside
  `internal/httpx`'s `Recover` middleware. A panic in any of them still kills the process —
  `Recover` only wraps the HTTP handler chain.
- `srv.Shutdown` still does not deliver close frames to hijacked WebSocket connections; a graceful
  shutdown still just cuts them when the process exits.

**A side effect worth naming:** reserving codes makes `POST /rides` load-bearing in a way it wasn't
before — a client can no longer join a convoy by guessing a plausible-looking code, only by holding
one that was actually minted. That's a real, if modest, access-control gain, given there is still
no JWT verification on `/ws` (`docs/ADR/ADR-008.md`'s deferred item).

## Future Revisions

- **Concurrent live rides reach the hundreds.** Shard `Hub.mu` — one lock per room, or one lock per
  shard of rooms hashed by code — instead of one lock for the whole process. The sweep goroutine's
  job doesn't change, only what it has to acquire per room.
- **The panic-recovery and hub-shutdown gaps above get their own fix.** If that work lands, revisit
  whether the sweep goroutine should be supervised the same way, since it's now the one goroutine
  every room's liveness depends on.
