# ADR-008: Two backends — Go for ephemeral realtime, Supabase for durable state

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-07-31 |
| **Deciders** | Horizon team |
| **Supersedes** | — |

## Context

The v2 pivot adds durable, user-owned data no version of Horizon needed before: accounts, ride
history, journal entries, photos, lifetime stats — the entire Return register. The existing Go hub
holds none of this and forgets every rider on restart, by design. `../PRODUCT.md`'s Backend
Direction names Supabase for exactly this; the open question is whether it replaces the Go hub or
sits beside it.

## Decision

**Keep the Go WebSocket server, and add Supabase alongside it. Each owns a disjoint half:**

| | **Go server** | **Supabase** |
|---|---|---|
| Owns | ephemeral, sub-second, fan-out | durable, user-owned, queryable |
| Holds | live convoy positions (in-memory), LiveKit tokens, ORS proxy | auth, rides, journal, photos, stats |
| Lifetime | dies with the ride | forever |
| **Never** | touches Postgres — no DB driver in `go.mod` | handles a live position stream |

**Identity flows one way.** Supabase Auth is the only issuer. The Go server *verifies* Supabase
JWTs (HS256, `SUPABASE_JWT_SECRET`) — it never mints identity, never has a user table, never
invents a session. Token transport is `Authorization: Bearer <jwt>` on the WS upgrade, **never a
query string**: `internal/httpx/logging.go` logs request URLs, so a token in the URL lands in logs
(redacting `Authorization` there is a follow-up). Native RN `WebSocket` supports a `headers` option
on the upgrade request — a benefit of having no browser client, which could not set headers there.
Use `github.com/golang-jwt/jwt/v5` for verification, do not hand-roll it — alg-confusion and
non-constant-time compares are where "standard library first" stops applying. This is the second
and last third-party Go dependency, after `gorilla/websocket`.

**Deviation from `../PRODUCT.md`:** its Backend Direction lists Supabase Realtime; live convoy uses
the Go server instead — sub-second fan-out at a fixed 4 Hz tick with server-side room state is what
the Go hub already does well, and Realtime is built for row-change subscriptions, not that.

## Alternatives Considered

**Supabase-only** — drop the Go hub, run convoy over Realtime. Rejected: throws away a working,
purpose-built fan-out loop for a changefeed not shaped for a 4 Hz positional stream, for zero
durability benefit — convoy state was never meant to be durable.

**Go-only** — keep everything in the existing binary. Rejected: nowhere to put ride history,
journal, or photos without reinventing a database and auth inside a server whose whole value is
being small and stateless.

## Consequences

Two systems to run instead of one; a JWT-verification path that must never diverge from Supabase's
signing config; one new failure mode — rejecting a wrongly-signed token.

## Future Revisions

Revisit if Supabase Realtime's throughput improves, or convoy state ever needs to be durable.
